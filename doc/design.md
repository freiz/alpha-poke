## 1. 目标与非目标

**目标**
- 构建一个强力的宝可梦对战 AI，水平接近或超越人类 pro。
- 完全在本地训练、测试各种方法（Python + uv + poke-env + 本地 Showdown）。
- 能系统地比较不同方法（BC / 离线 RL / 自博弈 / 搜索等），而不是只做一个一次性 bot。

**非目标（暂定）**
- 不做"每回合调用 LLM"的在线策略（证据显示在计时器内明显弱于 RL/搜索，见 R§8.4）；LLM 只作为离线 / 每局一次的辅助，见 D8。
- 不追求一次性覆盖所有赛制与世代；**双打 / VGC 暂不考虑**，只做 Gen9 OU 单打。
- 组队学习不是第一阶段的重点，但在计划内（见 D5、M5）。
- 不以公共天梯作为主要训练/迭代手段（只在最终评测时少量使用，见 D7）。

## 2. 问题特性

单打宝可梦对战是：双人零和、**不完全信息**（对手配置隐藏）、**同时选择动作**（每回合是一个约 9×9 的小矩阵博弈）、有随机性（伤害浮动/暴击/命中）、长时程（几十到上百回合），非随机赛制还要先**组队**。

设计上的含义：纯监督或纯 LLM 的天花板有限；已知的强系统都组合了"自博弈 RL + 对隐藏信息的推断/搜索"。

## 3. 调研结论摘要

完整证据与出处见 `research.md`，这里只列对设计影响最大的几条。

1. **已有系统在天梯上达到或接近顶尖人类，但最强的是闭源个人项目 `[自报]`**：Jaxcalibur（Gen9 随机对战，峰值 Elo 2557 / GXE 95.3，与最强人类持平）、mikumiku37（VGC Reg M-C 登顶，Elo 1857）。均未放出代码或权重。（R§2.2）
2. **公开可复现的路线有两条**：Metamon（离线 RL + 自博弈，Gen1 强，Gen9 OU 约 71% GXE）和 Foul Play（采样对手配置 + MCTS，Gen9 OU 约 80% GXE）。（R§3）
3. **配方已趋同**：小 transformer（8–60M）+ 极快的模拟器 + 自博弈（PPO/league）+ 测试时对采样"世界"做搜索（Jaxcalibur 自报约 +100–150 Elo）。（R§2.2、R§10）
4. **算力需求不大**（约 1 张 H100 × 1 周，或 1 张 RTX 5090 × 2 天），**瓶颈是模拟器吞吐**，不是 GPU。（R§2.2）
5. **Showdown 路径吞吐有限**：本机实测 poke-env + 多个本地服务器约 3.8k 回合/秒，直驱 `BattleStream` 多进程约 6.3k 回合/秒（随机策略、不含神经网络推理，见 D2 实测表）。单服务器上限约 1.3k 回合/秒，不随客户端数量增加。
6. **没有开源、已验证保真的快速 Gen9 / VGC 引擎**；可用的只有 advsim（Gen3 随机对战）和 pkmn/engine（Gen1–2，WIP）。（R§4.3）
7. **组队几乎没有成熟研究**；Gen9 OU 没有公开的顶尖水平 RL agent。（R§8.5、R§2.1）
8. **LLM 做在线策略明显更弱**（约 1300–1500 Elo）。（R§8.4）
9. **Metamon（源码级调研，`research_metamon.md`）**：最强公开模型 Kakuna（142M）Gen9 OU 自报约 71% GXE，明显弱于 Foul Play；观测空间有信息损失（无回合计数、无能力值/努力值/性格、不编码对手后备宝可梦）；依赖冻结的 poke-env 0.8.3.3 分叉，**不能与我们的 poke-env 0.16.1 同装一个 venv**。价值在于：评测对手、约 20GB 的 Gen9 OU 重建数据（后端无关的 `UniversalState` JSON）、训练配方。
10. **Foul Play（源码级调研，`research_foul_play.md`）**：无神经网络；强在对手建模（使用率 + 配置库 + 约 10 条硬编码推理规则 + 采样世界）加 DUCT-MCTS（手写估值函数）。Gen9 OU **每只宝可梦的配置独立采样，不考虑对手另外 5 只是什么**；硬淘汰加均匀抽样，不用似然。Foul Play 本体 GPL-3.0，poke-engine 为 MIT 但无与 Showdown 的一致性测试，只适合当搜索用近似模型。
11. **两个基线互补**：Metamon 对"人类风格/长期行为"建模强，Foul Play 对"机制精确计算与信息推断"强；超越它们需要"学习型策略/价值 + 信念模型 + 测试时搜索"，与 D3 一致。

## 4. 关键设计决策（讨论）

每个决策列出选项、权衡，并给出"倾向"。倾向是我基于调研的建议，等你确认或推翻。

### D1. 目标赛制

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. Gen9 随机对战** | 无组队；对手配置可由 `sets.json` 枚举（信念追踪容易）；数据量大（约 200 万 replay）；人类人口大，"持平顶尖人类"证据最清晰 | 没有官方职业赛事；含运气成分；对 bot 来说"超越 pro"的区分度主要在对局内决策 |
| **B. Gen9 OU** | 最大的官方单打人口（月约 57 万局）；开放空白最大（无公开顶尖 RL）；差距可测（榜首 1966 / GXE 85.7） | 要组队；隐藏空间大（太晶、努力值等）；Foul Play 已是强对手 |
| **C. Gen1–4 OU** | Metamon 数据与模型现成；pkmn/engine 可做快速模拟器 | 人口很小、天梯薄；非主流赛制，对"pro"的说服力弱 |
| **D. VGC 双打（Champions Reg M-x）** | 有真实职业圈 | 动作空间大；每个赛季规则变动、数据快速过期；机器 vs 职业选手的证据薄弱；无开源快速引擎 |

**已定（用户决定）**：**Gen9 OU 单打**。理由：随机对战里队伍随机，备战、选人、联动等层面的能力用不上，人类水平被拉低，不足以衡量"pro 水平"；Gen9 OU 才是有说服力的目标，也是公开资料里最大的空白（无公开的顶尖水平 RL agent）。

**信息可见性（Gen9 OU 天梯无 OTS）**：队伍预览只能看到对手 6 只的物种；招式、特性、道具、太晶属性在对局中逐步暴露；对手 HP 只显示百分比；努力值/性格/能力值永远不可见，只能靠伤害和速度关系推断。因此**对手配置信念模型是核心模块**，而不是可选项。

**后果**：
- 对局需要队伍，第一阶段用人类队伍池，组队学习列入后续阶段（见 D5）。
- 随机对战不再作为目标赛制；`sets.json` 的"配置可枚举"优势不存在，先验要靠 Smogon 使用率统计与 replay。
- 若自写快引擎，需覆盖 Gen9 OU 的机制（太晶、大量特性/招式），工作量比随机对战高。

### D2. 模拟器 / 训练基础设施

| 选项 | 说明 | 权衡 |
|---|---|---|
| **a. Showdown + poke-env** | 最简单，直接可用 | 实测整机约 3.8k 回合/秒（多服务器 + 多客户端）；适合评测与天梯部署 |
| **b. 直接驱动 `BattleStream`** | 绕开 websocket | 实测整机约 6.3k 回合/秒，只比 a 快约 1.6 倍；仍是单线程 Node，需自己写环境封装；有 Promise 竞态风险 |
| **c. 自写/移植快速引擎**（Rust / JAX / Warp / C） | 强 bot 作者都走了这条路（74.5 万–1520 万步/秒） | 工作量最大；必须对 Showdown 做一致性验证（advsim 的整局 + 决策点 + 伤害用例比对是范例）；Gen9 机制极多 |
| **d. 先用现成引擎验证方法** | advsim（Gen3 随机）/ pkmn/engine（Gen1–2） | 世代与目标赛制不一致，只验证方法 |

**M0 实测（2026-10-03，本机 AMD 79xx WSL 10 逻辑核；随机 vs 随机的 Gen9 OU，不含神经网络推理；脚本 `scripts/bench_poke_env.py`、`scripts/bench_battlestream.js`）**：

| 路径 | 配置 | 回合/秒 | 局/秒 |
|---|---|---|---|
| poke-env → 1 个服务器 | 1 进程，并发 1 | 747 | 13.2 |
| poke-env → 1 个服务器 | 1 进程，并发 10 | 1,350 | 23.9 |
| poke-env → 1 个服务器 | 4 个客户端进程 | 1,258 | 22.3 |
| poke-env → 4 个服务器 | 4 个客户端进程 | 2,619 | 46.0 |
| poke-env → 4 个服务器 | 8 个客户端进程 | **3,767** | 65.6 |
| poke-env → 8 个服务器 | 8 个客户端进程 | 3,057 | 54.2 |
| 直驱 `BattleStream` | 1 个 node 进程 | 1,355 | 49.9 |
| 直驱 `BattleStream` | 4 个 node 进程 | 4,445 | — |
| 直驱 `BattleStream` | 8 个 node 进程 | **6,261** | — |

解读：
- **单个 Showdown 服务器的上限约 1.3k 回合/秒**，客户端进程再多也不会提高；要扩展必须多开服务器。
- 整机约 10 逻辑核时，poke-env 路径约 3.8k 回合/秒，8 服务器 + 8 客户端反而更低（CPU 被服务器和 Python 客户端抢满）。
- 直驱 `BattleStream` 比 poke-env 路径只快约 1.6 倍，不是数量级提升；Python 客户端的解析开销和服务器开销大致相当。
- 一局约 50 回合，3.8k 回合/秒 ≈ 70 局/秒 ≈ 每天约 600 万局；**1 亿局约需 16 天**，且此数字**还没算神经网络推理**。比原先按 681 步/秒推算的"几个月"乐观得多，但仍明显低于 Jaxcalibur / mikumiku37 的自写引擎（74.5 万–1520 万步/秒）。
- 局限：随机策略的对局长度、WSL 下 10 逻辑核、基准运行期间有调研子任务占用少量 CPU；未包含批量 GPU 推理、`BattleStream` 直驱的是随机 AI（对局偏短，约 27 回合/局）。

**倾向**：M0 实测表明 a 对中等规模自博弈（10^6–10^7 局）够用，b 的收益有限，因此**先用 a（poke-env → 多个本地服务器）作为训练与评测的统一路径**，不急着自写引擎；等加入神经网络推理后再实测端到端吞吐，据此决定是否投入 **c**（目标是 10^8 局级别时才有必要）。**poke-env 保留为评测/部署接口**，训练环境与评测环境共用同一套观测/动作编码，避免 sim2sim 偏差。

### D3. 算法路线

可分层叠加，不必互斥：

1. **基线层**：启发式（poke-env 自带）、Foul Play、Metamon checkpoint——作为对照标尺与评测对手。
2. **学习层**：
   - (i) BC / 离线 RL（Metamon 路线，需要 replay 重建管线）；
   - (ii) 自博弈 RL：PPO + league；可加 KL-to-anchor / MMD 类正则化缓解循环（R§8.1）；可加 oracle guiding（训练时让 critic/教师看到对手真实配置）。
3. **决策时层**：对手配置信念 + 采样 K 个世界 + 深度受限搜索 + 根节点同时动作矩阵求解（Jaxcalibur / mikumiku37 / PokaiTrainer / Ataraxos 的共同模式）。其中**信念模型**单独成项，见 D8。

**倾向**：学习层先做 **(ii) 自博弈 + 辅助的对手配置预测头**（Gen9 OU 下信念建模是核心），用 (i) 的人类数据（Metamon 的 Gen9 OU 数据）做预训练——在 OU 里 BC 初始化更重要，因为配置先验主要来自人类数据；决策时层作为第二阶段，在有可用的快速模拟器之后再加。理由：公开证据显示"策略网络单独不够，搜索贡献大"（PokaiTrainer），但搜索需要快模拟器与信念模型，成本更高，不应在基础设施未定时先做。

### D4. 复用 vs 自研

| 资源 | 许可 | 建议用法 |
|---|---|---|
| Metamon 代码/checkpoint/AMAGO | MIT | 可作为基线、评测对手、解析器参考；可直接复用 |
| Metamon 解析后的数据集 | **CC-BY-NC-4.0** | 个人研究可用；若将来商用需注意 |
| Foul Play | **GPL-3.0** | 作为外部对手/参考实现使用；复制代码进本项目会带来传染性 |
| poke-engine | MIT | 可作为搜索用近似引擎的参考或依赖（世代覆盖需先核实） |
| PokéChamp | NOASSERTION | 复用前先看 LICENSE |

**倾向**：把 Metamon 与 Foul Play 当作**基线与评测对手**，核心训练栈自研（这是"本地训练、测试各种方法"的初衷）；数据集管线优先复用 Metamon 的重建思路。

**来自源码级调研的具体结论**（详见两份报告的 §9）：
- **Metamon**：评测对手立刻可做（独立 venv + `ChallengeByUsername` acceptor，需要 flash-attn / CUDA，1–3 人日）；**复用数据而非代码**——直接读 `metamon-parsed-replays/gen9ou` 的 `UniversalState` JSON，用我们自己的观测编码训练；不要重写 4k+ 行的 replay parser；观测空间重新设计；本地端口硬编码为 8000。
- **Foul Play**：只作**独立进程评测对手**（约 0.5–1 天；独立 venv，Rust 工具链，`--team-name gen9/ou`；登录与数据下载默认联网，离线需预热缓存并给 `login()` 打补丁，符合"不连公共服务器"原则）；**不 import `fp.*`**，集合推断规则 clean-room 重写；作者托管的 `data.foulplay.cc` 配置库许可未声明，不直接使用；poke-engine（MIT）可依赖/vendor/fork，但仅作搜索用近似模型，不作训练真值。

### D5. 组队

文献几乎空白（R§8.5），是潜在的差异化点。这里的"组队"指赛前自己挑 6 只宝可梦并配招式/道具/努力值/太晶（与双打无关）。**已定（用户决定）：组队纳入计划，但第一阶段不重点做**，先使用人类队伍，待对战 agent 足够强后再作为正式阶段推进（M5）。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 固定 1 支队 | 最简单，单队最容易练强，评测最干净 | 无法验证泛化，易被针对 |
| **小队伍池（约 5–10 支）** | 学的是"怎么打"而非"打这一队"；评测可随机抽队 | 训练更慢，单队强度略低（VGC-Bench：队伍越多，单队表现越差） |
| 大队伍池（Metamon 有约 13.9 万支 Gen9 队伍） | 泛化最好 | 最难训练 |

**倾向**：小队伍池，来源 Smogon 样例队伍与高分天梯队伍，覆盖进攻/平衡/防守等打法；若第一版训练不稳再收窄为 1 支。注意 Metamon 作者提到对样例队伍有过拟合，池里要有足够多样性。

**说明**：
- OU 单打是 6 打 6，没有"带哪 4 只"的选择，队伍预览只选首发，不增加动作空间复杂度。
- 对手的队伍不可控，agent 必须能应对各种队伍，与自己用哪支队无关。
- "超越 pro"的声明需限定为"使用同一批人类队伍、对局内决策更强"，与公开工作的通行口径一致。
- 队伍编码/观测不依赖谁来选队，将来接入组队模块不需要重做。
- 后期方向（R§8.5）：以元博弈看待队伍（PSRO/double oracle 求不可利用的队伍混合）；用人类队伍预训练的集合生成器 + 以对战 agent 池的胜率为奖励微调；用代理胜率模型做筛选。

### D6. 算力预算

**本机（用户提供）**：AMD 79xx（AM5，应为 7900X/7950X，12–16 核 / 24–32 线程）、64GB 内存、RTX 4070 Ti（12GB 显存）。**可以租云 GPU**。

公开配方的量级：1×H100×约 1 周（Jaxcalibur）、1×RTX 5090×约 2 天（mikumiku37），**两者都配自写快引擎**；用 Showdown 作模拟器则 CPU 核数是瓶颈，GPU 反而闲着。

**对本机的粗略判断（基于 M0 实测的估算，未含神经网络推理）**：
- **GPU 够用**：目标模型 5–60M 参数，12GB 显存足够训练和批量推理；4070 Ti 不是瓶颈。
- **瓶颈在模拟器**：M0 实测 Showdown 路径整机约 3.8k–6.3k 回合/秒（见 D2 实测表）。按每局约 50 回合，**10^7 局约需 1.5–3 天、10^8 局约需 2–3 周**，尚未计入神经网络推理开销。因此"本机直接用 Showdown 做中等规模自博弈（10^6–10^7 局）"是可行的；要到 Jaxcalibur 级别的 10^8 局则需要租多核 CPU 或自写引擎。
- **云 GPU 的价值有限**：租 GPU 解决不了 CPU 引擎的瓶颈。更有价值的云用法：
  1. 在 Metamon 数据上做**大模型离线预训练 / 监督训练**（GPU 受限的任务）；
  2. 需要横向扩展自博弈时，租**多核 CPU 机器**（或 CPU+GPU 机器）；
  3. 若将来自写 GPU 引擎（Warp/JAX），再租高端 GPU。

**倾向**：本地开发与小规模实验；先实测吞吐，**再决定要不要租云**以及租什么（高核数 CPU 往往比高端 GPU 更划算）。

### D7. 评测协议

- **本地为主**：固定队伍池、双方互换座位的 head-to-head 胜率矩阵；Bradley-Terry / Glicko 评分 + bootstrap 置信区间；对手含启发式、Foul Play、Metamon checkpoint、历史 checkpoint。
- **样本量**：每个对阵至少 400 局（95% 置信半宽约 ±4.9 个百分点）；要检出 55% vs 50% 约需 615 局（R§9.4）。
- **可利用度代理**：训练一个 RL 利用者去打冻结的 agent，报告其胜率（R§8.2）。
- **公共天梯**：**当前阶段不连接公共服务器**（agent 还太弱；代码里 `alpha_poke.servers.local_server` 只允许本机地址）。将来仅用于最终 checkpoint，用新开的、明确命名的账号，几百局为限；用 Glicko-1/GXE 而非裸 Elo；不在低人口天梯或 suspect 测试期间跑大量局。Showdown 无明确 bot 条款，但社区态度偏负面（R§9.6）。
- **注意**：Metamon 的本地 GXE 与公共天梯 GXE 无对应关系，不能直接比。

### D8. 对手信念模型，以及 LLM 的位置

**背景**：Gen9 OU 没有 OTS，信念模型是核心模块（见 D1）。Foul Play 的对手建模是目前公开最强的实现，但有明确的缺口（`research_foul_play.md` §2）：

| Foul Play 做了 | Foul Play 没做 |
|---|---|
| 使用率 + 配置库（Gen9 OU 约 349 物种 / 4,738 套）+ 约 10 条硬编码规则（速度区间、围巾、选择道具、突击背心、Boots、反推伤害等）逐步淘汰候选 | **Gen9 下每只宝可梦独立采样，不考虑对手另外 5 只**（队友共现只用于 Gen1–4 补全未知宝可梦） |
| 每次决策采样若干完整世界，各自跑 MCTS 后汇总 | 采样时均匀抽样（刻意不按 count），无似然；硬淘汰而非后验 |
| 队伍预览选首发也复用同一套采样加搜索 | 只用"出现了什么"，不用"对手为什么选这招"；不显式给出战术分析 |

**想法（用户提出，已讨论）**：看对手整队的构成 → 判断打法类型（如撒菱队）、可能的配招 → 我方最好的应对。不需要每个动作都调用 LLM。**结论：这是对 Foul Play 信念模块的升级，核心是"整队条件下的联合先验 + 软似然后验"，LLM 只是其中一种可选实现。**

**升级方案**：
1. **整队条件先验** `P(各只配置 | 对手 6 只物种)`：队伍里角色互补（通常 1 个隐形岩手、有 Spin 手等），独立采样会采出不合理世界。
2. **软似然后验**：先验 × 本场观察的似然（伤害、速度顺序、出招选择、道具/特性触发），替代硬淘汰，容忍引擎伤害计算误差，并能利用行为信息。
3. **整队一致性采样**供搜索使用（采样出的 K 个世界应是"像真实队伍"的世界）。

**实现候选**：

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 在人类队伍上训练的掩码补全模型**（推荐起步） | 条件为已知物种/已揭示信息，补全其余配置；Metamon 的实验性 `TeamPredictionModel`（masked-token transformer + MaskGIT）即此思路；数据：Metamon Gen9 队伍约 13.9 万支 + 使用率统计的 Teammates | 输出校准的概率、无幻觉、推理几乎免费 |
| B. 使用率统计 + 队友共现的条件先验 | 不训练，查表式 | 最便宜的基线，必须先打败它才能说学习型模型有价值 |
| C. LLM（零样本/少样本） | 给出打法类型、可能配置、首发建议的结构化 JSON | 可能在**罕见宝可梦、新版本统计稀薄**时有优势；需用 Showdown 数据校验输出，防幻觉 |

**LLM 的位置（结论）**：

| 用法 | 评价 |
|---|---|
| 每回合在线调用 | **不做**：延迟（PokéChamp 约 1/3 对局因超时输掉）、训练不可行、缺乏结果反馈、证据偏负面（R§8.4） |
| **队伍预览时调用一次**（打法类型、可能配置、首发建议，结构化输出） | **值得做成实验**；延迟不是问题；输出接入配置先验 / 首发选择 / 网络条件输入，三处可分别验证 |
| 组队（M5）、对局复盘与调试、批量标注队伍 | 价值高，离线、无延迟约束，LLM 提议加胜率闭环 |
| 辅助标签（给 replay 标"胜利路线"作为辅助预测目标） | 中，未验证 |

**注意**：
- **训练与部署分布不一致**：若把 LLM 输出当网络输入特征，自博弈的小队伍池（约 10 支）只会产生约 100 个队伍配对，网络易过拟合这些标签。办法：只把 LLM 输出当先验/首发建议使用（推荐先走这条），或用 Metamon 的 13.9 万支队伍批量标注以拓宽分布。
- **要打败的非 LLM 基线**：首发选择可用我们自己的价值网络算 6×6 首发对阵表；配置先验有方案 B。

**离线证伪实验（不需要打对局）**：用带真实队伍的数据（Metamon 重建数据，或自博弈中已知真值），从对局开头的预览出发，比较各先验给**真实配置**的对数似然与 top-k 命中率：Foul Play 式（独立 + 均匀）、方案 B、方案 A、方案 C（LLM）。若 A/C 显著优于 Foul Play 式，再进入对局实验（把新采样器接入搜索，对比 Foul Play 的胜率）；若无显著提升，则及早放弃，成本很低。Foul Play 作者未公开度量过预测准确率，所以**提升空间未知**，这个实验就是为了先搞清楚它。

**离线评测结果（2026-10-04，`doc/belief_prior_eval.md`）**：按时间切分的高分 replay 上，整队条件先验（认出被照搬的队伍，回退到核心条件，再回退到物种分布）对暴露道具的 top-1 准确率 76.6%、太晶 68.2%、招式 recall@4 84.3%；Smogon 边缘分布分别只有 55.4%、50.4%、73.3%。对训练集中见过的队伍（约占一半）分别达到 92.1%、83.3%、94.7%。**D8 的核心假设得到验证**。

**许可**：clean-room 重做，不复制 `fp/` 代码，不直接使用作者托管的 `data.foulplay.cc` 数据；可用的数据：Smogon stats、Showdown `data/`、Metamon 数据集（CC-BY-NC-4.0）。

### D9. 知识驱动原型（模仿人类学习过程）与分层套路表示

**已定（用户提出，2026-10-04 讨论）**：先做一个模仿人类学习过程的原型——先熟悉宝可梦和招式，再"看攻略"学套路和配招，然后演练；掌握的套路越多，越能预测对手并反制。重点是**长期规划**，短期动作先粗糙，之后再换成学习型/搜索型的动作选择与评测。

**模块划分**（每层可单独验证，且都是以后搜索 / RL 会复用的资产）：

| 人类学习过程 | 模块 | 数据来源 | 验证方式 |
|---|---|---|---|
| 熟悉宝可梦和招式 | 知识层：图鉴、招式、属性克制、伤害计算 | Showdown 数据、poke-env（`GenData`、`calc`） | 与 Showdown 伤害计算对拍 |
| 看攻略学套路、配招 | 套路库：分层套路表示（见下） | Smogon 统计 + 高分 replay（`doc/analysis_gen9ou.md`）；LLM 命名与解释；可选 Smogon 攻略文本 | 人工抽查；覆盖率 |
| 预测对手 | 信念层：先验（队伍预览）+ 对局中更新 | 套路库 + 对局观察 | 离线证伪实验（D8）：对后续暴露配置的对数似然 / top-k |
| 长期规划 | 规划层：对手类型、主要威胁、我方 win condition、首发、需保留的宝可梦 | 伤害计算 + 信念；可选 LLM（每局一次，D8） | 首发选择 A/B、对局胜率 |
| 短期动作 | 动作层：先用启发式（伤害计算 + 计划权重） | — | 对 poke-env 基线、再对 Foul Play 的胜率 |

风险：动作层长期停留在启发式会限制整体强度（Foul Play 强在精确计算 + 搜索），所以原型的主要价值在前四层；动作层后续由搜索 / RL 替换，计划作为其条件输入或估值偏置。

**分层套路表示**：

| 层 | 内容 | 表示 |
|---|---|---|
| L0 单只配置 | 物种 + 道具、特性、太晶、招式、努力值 | 配置的概率分布（Smogon 统计 + replay） |
| L1 角色 | 撒钉、清钉、开天气、天气受益者、pivot、强化收割、受盾、速度控制、破盾等 | 由招式/特性/道具推出的多标签 |
| L2 核心（2–4 只） | 刻意搭配的小组 | 频繁项集，但**只保留"最大核心"**：k 只组合的 lift 必须明显高于它的每个 (k−1) 子集，否则并入子集（实验表明不去冗余时，前几名 3/4 只组合全是同一受队外壳的子集） |
| L3 整队类型 | 一支队可同时属于多个类型（如"晴天 + 撒钉"） | 软聚类（NMF / 主题模型），每支队得到类型的**混合比例**；替换当前的硬 k-means |

各层之间是包含关系（类型 ← 核心 ← 角色/宝可梦 ← 配置分布）。用途：
- **信念**：预览时由 6 只物种推断所属核心与类型，再得到每只的配置先验；
- **规划**：计划按核心表述（如"对方胜利路线是雨天收割，优先处理 Pelipper"）；
- **组队（M5）**：以核心为积木拼队。

数据限制：物种在预览时全部可见，所以 L2/L3 只靠物种即可做扎实；L0/L1 依赖已暴露信息与 Smogon 统计，会不完整。

**LLM 选型（已定，2026-10-04，依据 `doc/llm_benchmark.md`）**：通过 OpenRouter 调用（key 在项目级 `.env`，不入库；全局预算上限 `LLM_BUDGET_USD`）。快速、批量任务默认 `google/gemini-3.8-flash`；高质量任务以后考虑 Claude Opus 5.5（先在 benchmark 与盲评上验证）。全程英文输入输出并要求输出与输入数据一致。benchmark 结论：LLM 凭记忆补全配置远不如数据驱动的信念先验，只用于基于数据的总结、命名与（之后的）预览计划。

**推进顺序（已确认）**：
1. L1 角色标签 + L2 最大核心挖掘 + L3 软聚类，替换现有硬聚类；
2. 信念先验离线评测（D8 实验）：用预览的 6 只物种预测后续暴露的配置，比较使用率统计、核心条件先验等；
3. 配好 API key 后，用 LLM 为套路命名、写说明，并试验预览时的结构化计划；
4. 规划层 + 启发式动作层，接入本地对战评测。

| 风险 | 说明 / 缓解 |
|---|---|
| 吞吐不足 | M0 实测整机约 3.8k 回合/秒（未含神经网络推理）；10^8 局约需 2–3 周，需加入推理后再实测，必要时租多核 CPU 或走 D2 的 c |

| LLM 辅助的收益不确定 | 只放在预览时 / 离线；必须先打败非 LLM 基线（D8） |
| 自写引擎不保真 | 机制极多；必须做整局 + 决策点 + 伤害用例的一致性验证 |
| 自博弈循环 / 可被利用 | 队伍相克有非传递环；用 KL 正则、league、利用者监控 |
| 评测噪声 | 局数不足会得出错误结论；固定队伍池、互换座位、报置信区间 |
| 数据过期（VGC） | 规则每季度变动；暂缓 VGC |
| sim-to-real / sim2sim 差距 | 训练与部署共用观测编码；定期用真实服务器回归 |
| 许可 / 规则 | Metamon 数据非商用；Foul Play GPL；Showdown 天梯对 bot 的态度模糊 |
| 目标可能超出范围 | 顶尖闭源 bot 靠的是数月开发 + 自写引擎；需合理设定阶段性目标 |
