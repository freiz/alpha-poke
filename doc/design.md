## 1. 目标与非目标

**目标**
- 构建一个强力的宝可梦对战 AI，水平接近或超越人类 pro。
- 完全在本地训练、测试各种方法（Python + uv + poke-env + 本地 Showdown）。
- 能系统地比较不同方法（BC / 离线 RL / 自博弈 / 搜索等），而不是只做一个一次性 bot。

**非目标（暂定）**
- 不做 LLM 在线策略（证据显示在计时器内明显弱于 RL/搜索，见 R§8.4）。
- 不追求一次性覆盖所有赛制与世代；**双打 / VGC 暂不考虑**，只做 Gen9 OU 单打。
- 组队学习不是第一阶段的重点，但在计划内（见 D5、M5）。
- 不以公共天梯作为主要训练/迭代手段（只在最终评测时少量使用，见 D7）。

## 2. 问题特性

单打宝可梦对战是：双人零和、**不完全信息**（对手配置隐藏）、**同时选择动作**（每回合是一个约 9×9 的小矩阵博弈）、有随机性（伤害浮动/暴击/命中）、长时程（几十到上百回合），非随机赛制还要先**组队**。

设计上的含义：纯监督或纯 LLM 的天花板有限；已知的强系统都组合了"自博弈 RL + 对隐藏信息的推断/搜索"。

## 3. 调研结论摘要

完整证据与出处见 `research.md`，这里只列对设计影响最大的几条。

1. **已有系统在天梯上达到或接近顶尖人类，但最强的是闭源个人项目 `[自报]`**：Jaxcalibur（Gen9 随机对战，峰值 Elo 2557 / GXE 95.3，与最强人类持平）、mikumiku37（VGC Reg M-C 登顶，Elo 1857）。均未放出代码或权重。（R§2.2）
2. **公开可复现的路线有两条**：Metamon（离线 RL + 自博弈，Gen1 强，Gen9 OU 约 71% GXE）和 Foul Play（采样对手配置 + MCTS，Gen9 OU 约 80% GXE）。（R§3）
3. **配方已趋同**：小 transformer（8–60M）+ 极快的模拟器 + 自博弈（PPO/league）+ 测试时对采样"世界"做搜索（Jaxcalibur 自报约 +100–150 Elo）。（R§2.2、R§10）
4. **算力需求不大**（约 1 张 H100 × 1 周，或 1 张 RTX 5090 × 2 天），**瓶颈是模拟器吞吐**，不是 GPU。（R§2.2）
5. **Showdown 路径吞吐有限**：本机实测 poke-env + 多个本地服务器约 3.8k 回合/秒，直驱 `BattleStream` 多进程约 6.3k 回合/秒（随机策略、不含神经网络推理，见 D2 实测表）。单服务器上限约 1.3k 回合/秒，不随客户端数量增加。
6. **没有开源、已验证保真的快速 Gen9 / VGC 引擎**；可用的只有 advsim（Gen3 随机对战）和 pkmn/engine（Gen1–2，WIP）。（R§4.3）
7. **组队几乎没有成熟研究**；Gen9 OU 没有公开的顶尖水平 RL agent。（R§8.5、R§2.1）
8. **LLM 做在线策略明显更弱**（约 1300–1500 Elo）。（R§8.4）

## 4. 关键设计决策（讨论）

每个决策列出选项、权衡，并给出"倾向"。倾向是我基于调研的建议，等你确认或推翻。

### D1. 目标赛制

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. Gen9 随机对战** | 无组队；对手配置可由 `sets.json` 枚举（信念追踪容易）；数据量大（约 200 万 replay）；人类人口大，"持平顶尖人类"证据最清晰 | 没有官方职业赛事；含运气成分；对 bot 来说"超越 pro"的区分度主要在对局内决策 |
| **B. Gen9 OU** | 最大的官方单打人口（月约 57 万局）；开放空白最大（无公开顶尖 RL）；差距可测（榜首 1966 / GXE 85.7） | 要组队；隐藏空间大（太晶、努力值等）；Foul Play 已是强对手 |
| **C. Gen1–4 OU** | Metamon 数据与模型现成；pkmn/engine 可做快速模拟器 | 人口很小、天梯薄；非主流赛制，对"pro"的说服力弱 |
| **D. VGC 双打（Champions Reg M-x）** | 有真实职业圈 | 动作空间大；每个赛季规则变动、数据快速过期；机器 vs 职业选手的证据薄弱；无开源快速引擎 |

**已定（用户决定）**：**Gen9 OU 单打**。理由：随机对战里队伍随机，备战、选人、联动等层面的能力用不上，人类水平被拉低，不足以衡量"pro 水平"；Gen9 OU 才是有说服力的目标，也是公开资料里最大的空白（无公开的顶尖水平 RL agent）。

**信息可见性（Gen9 OU 天梯无 OTS）**：队伍预览只能看到对手 6 只的物种；招式、特性、道具、太晶属性在对局中逐步暴露；对手 HP 只显示百分比；努力值/性格/能力值永远不可见，只能靠伤害和速度关系推断。因此**对手配置信念模型是核心模块**，而不是可选项。

**后果**：
- 对局需要队伍，第一阶段用人类队伍池，组队学习列入后续阶段（见 D5）。
- 随机对战不再作为目标赛制；`sets.json` 的"配置可枚举"优势不存在，先验要靠 Smogon 使用率统计与 replay。
- 若自写快引擎，需覆盖 Gen9 OU 的机制（太晶、大量特性/招式），工作量比随机对战高。

### D2. 模拟器 / 训练基础设施

| 选项 | 说明 | 权衡 |
|---|---|---|
| **a. Showdown + poke-env** | 最简单，直接可用 | 吞吐低（待实测）；适合评测与天梯部署 |
| **b. 直接驱动 `BattleStream`** | 绕开 websocket | 吞吐明显更高（裸 Showdown 约 2 万步/秒，间接数字）；仍是单线程 Node，需自己写环境封装；有 Promise 竞态风险 |
| **c. 自写/移植快速引擎**（Rust / JAX / Warp / C） | 强 bot 作者都走了这条路（74.5 万–1520 万步/秒） | 工作量最大；必须对 Showdown 做一致性验证（advsim 的整局 + 决策点 + 伤害用例比对是范例）；Gen9 机制极多 |
| **d. 先用现成引擎验证方法** | advsim（Gen3 随机）/ pkmn/engine（Gen1–2） | 世代与目标赛制不一致，只验证方法 |

**M0 实测（2026-10-03，本机 AMD 79xx WSL 10 逻辑核；随机 vs 随机的 Gen9 OU，不含神经网络推理；脚本 `scripts/bench_poke_env.py`、`scripts/bench_battlestream.js`）**：

| 路径 | 配置 | 回合/秒 | 局/秒 |
|---|---|---|---|
| poke-env → 1 个服务器 | 1 进程，并发 1 | 747 | 13.2 |
| poke-env → 1 个服务器 | 1 进程，并发 10 | 1,350 | 23.9 |
| poke-env → 1 个服务器 | 4 个客户端进程 | 1,258 | 22.3 |
| poke-env → 4 个服务器 | 4 个客户端进程 | 2,619 | 46.0 |
| poke-env → 4 个服务器 | 8 个客户端进程 | **3,767** | 65.6 |
| poke-env → 8 个服务器 | 8 个客户端进程 | 3,057 | 54.2 |
| 直驱 `BattleStream` | 1 个 node 进程 | 1,355 | 49.9 |
| 直驱 `BattleStream` | 4 个 node 进程 | 4,445 | — |
| 直驱 `BattleStream` | 8 个 node 进程 | **6,261** | — |

解读：
- **单个 Showdown 服务器的上限约 1.3k 回合/秒**，客户端进程再多也不会提高；要扩展必须多开服务器。
- 整机约 10 逻辑核时，poke-env 路径约 3.8k 回合/秒，8 服务器 + 8 客户端反而更低（CPU 被服务器和 Python 客户端抢满）。
- 直驱 `BattleStream` 比 poke-env 路径只快约 1.6 倍，不是数量级提升；Python 客户端的解析开销和服务器开销大致相当。
- 一局约 50 回合，3.8k 回合/秒 ≈ 70 局/秒 ≈ 每天约 600 万局；**1 亿局约需 16 天**，且此数字**还没算神经网络推理**。比原先按 681 步/秒推算的"几个月"乐观得多，但仍明显低于 Jaxcalibur / mikumiku37 的自写引擎（74.5 万–1520 万步/秒）。
- 局限：随机策略的对局长度、WSL 下 10 逻辑核、基准运行期间有调研子任务占用少量 CPU；未包含批量 GPU 推理、`BattleStream` 直驱的是随机 AI（对局偏短，约 27 回合/局）。

**倾向**：先做 **a + b** 并**实测吞吐**（见第 8 节）；如果吞吐不足以支撑自博弈规模，再决定是否投入 **c**。**无论如何，poke-env 保留为评测/部署接口**，训练环境与评测环境要共用同一套观测/动作编码，避免 sim2sim 偏差。

### D3. 算法路线

可分层叠加，不必互斥：

1. **基线层**：启发式（poke-env 自带）、Foul Play、Metamon checkpoint——作为对照标尺与评测对手。
2. **学习层**：
   - (i) BC / 离线 RL（Metamon 路线，需要 replay 重建管线）；
   - (ii) 自博弈 RL：PPO + league；可加 KL-to-anchor / MMD 类正则化缓解循环（R§8.1）；可加 oracle guiding（训练时让 critic/教师看到对手真实配置）。
3. **决策时层**：对手配置信念 + 采样 K 个世界 + 深度受限搜索 + 根节点同时动作矩阵求解（Jaxcalibur / mikumiku37 / PokaiTrainer / Ataraxos 的共同模式）。

**倾向**：学习层先做 **(ii) 自博弈 + 辅助的对手配置预测头**（Gen9 OU 下信念建模是核心），用 (i) 的人类数据（Metamon 的 Gen9 OU 数据）做预训练——在 OU 里 BC 初始化更重要，因为配置先验主要来自人类数据；决策时层作为第二阶段，在有可用的快速模拟器之后再加。理由：公开证据显示"策略网络单独不够，搜索贡献大"（PokaiTrainer），但搜索需要快模拟器与信念模型，成本更高，不应在基础设施未定时先做。

### D5. 组队

文献几乎空白（R§8.5），是潜在的差异化点。这里的"组队"指赛前自己挑 6 只宝可梦并配招式/道具/努力值/太晶（与双打无关）。**已定（用户决定）：组队纳入计划，但第一阶段不重点做**，先使用人类队伍，待对战 agent 足够强后再作为正式阶段推进（M5）。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 固定 1 支队 | 最简单，单队最容易练强，评测最干净 | 无法验证泛化，易被针对 |
| **小队伍池（约 5–10 支）** | 学的是"怎么打"而非"打这一队"；评测可随机抽队 | 训练更慢，单队强度略低（VGC-Bench：队伍越多，单队表现越差） |
| 大队伍池（Metamon 有约 13.9 万支 Gen9 队伍） | 泛化最好 | 最难训练 |

**倾向**：小队伍池，来源 Smogon 样例队伍与高分天梯队伍，覆盖进攻/平衡/防守等打法；若第一版训练不稳再收窄为 1 支。注意 Metamon 作者提到对样例队伍有过拟合，池里要有足够多样性。

**说明**：
- OU 单打是 6 打 6，没有"带哪 4 只"的选择，队伍预览只选首发，不增加动作空间复杂度。
- 对手的队伍不可控，agent 必须能应对各种队伍，与自己用哪支队无关。
- "超越 pro"的声明需限定为"使用同一批人类队伍、对局内决策更强"，与公开工作的通行口径一致。
- 队伍编码/观测不依赖谁来选队，将来接入组队模块不需要重做。
- 后期方向（R§8.5）：以元博弈看待队伍（PSRO/double oracle 求不可利用的队伍混合）；用人类队伍预训练的集合生成器 + 以对战 agent 池的胜率为奖励微调；用代理胜率模型做筛选。

### D6. 算力预算

**本机（用户提供）**：AMD 79xx（AM5，应为 7900X/7950X，12–16 核 / 24–32 线程）、64GB 内存、RTX 4070 Ti（12GB 显存）。**可以租云 GPU**。

公开配方的量级：1×H100×约 1 周（Jaxcalibur）、1×RTX 5090×约 2 天（mikumiku37），**两者都配自写快引擎**；用 Showdown 作模拟器则 CPU 核数是瓶颈，GPU 反而闲着。

**对本机的粗略判断（我的估算，未实测，需用第 8 节的基准校准）**：
- **GPU 够用**：目标模型 5–60M 参数，12GB 显存足够训练和批量推理；4070 Ti 不是瓶颈。
- **瓶颈在模拟器**：M0 实测 Showdown 路径整机约 3.8k–6.3k 回合/秒（见 D2 实测表）。按每局约 50 回合，**10^7 局约需 1.5–3 天、10^8 局约需 2–3 周**，尚未计入神经网络推理开销。因此"本机直接用 Showdown 做中等规模自博弈（10^6–10^7 局）"是可行的；要到 Jaxcalibur 级别的 10^8 局则需要租多核 CPU 或自写引擎。
- **云 GPU 的价值有限**：租 GPU 解决不了 CPU 引擎的瓶颈。更有价值的云用法：
  1. 在 Metamon 数据上做**大模型离线预训练 / 监督训练**（GPU 受限的任务）；
  2. 需要横向扩展自博弈时，租**多核 CPU 机器**（或 CPU+GPU 机器）；
  3. 若将来自写 GPU 引擎（Warp/JAX），再租高端 GPU。

**倾向**：本地开发与小规模实验；先实测吞吐，**再决定要不要租云**以及租什么（高核数 CPU 往往比高端 GPU 更划算）。

### D7. 评测协议

- **本地为主**：固定队伍池、双方互换座位的 head-to-head 胜率矩阵；Bradley-Terry / Glicko 评分 + bootstrap 置信区间；对手含启发式、Foul Play、Metamon checkpoint、历史 checkpoint。
- **样本量**：每个对阵至少 400 局（95% 置信半宽约 ±4.9 个百分点）；要检出 55% vs 50% 约需 615 局（R§9.4）。
- **可利用度代理**：训练一个 RL 利用者去打冻结的 agent，报告其胜率（R§8.2）。
- **公共天梯**：**当前阶段不连接公共服务器**（agent 还太弱；代码里 `alpha_poke.servers.local_server` 只允许本机地址）。将来仅用于最终 checkpoint，用新开的、明确命名的账号，几百局为限；用 Glicko-1/GXE 而非裸 Elo；不在低人口天梯或 suspect 测试期间跑大量局。Showdown 无明确 bot 条款，但社区态度偏负面（R§9.6）。
- **注意**：Metamon 的本地 GXE 与公共天梯 GXE 无对应关系，不能直接比。

## 5. 暂定架构草图（非最终）

```
                ┌───────────────────────────────┐
                │  训练环境（D2 决定具体实现）     │
                │  Showdown BattleStream / 快引擎 │
                └──────────────┬────────────────┘
                               │ 统一的观测/动作编码（envs/）
        ┌──────────────────────┴──────────────────────┐
        │ 策略网络（agents/）                            │
        │  实体 token 编码（己方6 / 对方6 / 场地）          │
        │  + 跨回合因果 transformer                      │
        │  头：策略(带掩码) / 价值 / 对手配置预测(辅助)      │
        └──────────────────────┬──────────────────────┘
                               │
   训练（training/）：[可选 BC 预训练] → 自博弈 PPO + league（+KL 正则）
   决策时（agents/）：信念采样 K 世界 → 浅层搜索 → 根节点矩阵求解（第二阶段）
   评测（eval/）：poke-env 接口，本地胜率矩阵 / BT 评分 / 利用者 / 天梯（少量）
```

要点（来自调研的共识，R§10）：模型保持小（5–60M）以便批量推理；动作掩码；奖励以胜负为主、塑形要小并退火；保留人类数据训练的锚点防止自博弈漂移；按回合追踪价值网络校准。

## 6. 里程碑草案（依赖 D1–D3 的确认，可调整）

1. **M0 基础设施**：本地 Showdown 跑通；poke-env 对战基线（Random / MaxBasePower / SimpleHeuristics）；吞吐实测。
2. **M1 评测框架**：胜率矩阵、BT 评分、置信区间；接入 Foul Play 与 Metamon checkpoint 作为参照对手；得到"基线标尺"。
3. **M2 第一个学习型 agent**：Gen9 OU 的统一观测/动作编码 + 固定队伍池 + 对手配置先验（Smogon 使用率）；先 BC/自博弈 PPO 跑通管线。
4. **M3 吞吐与规模**：按 D2 的结论决定是否上自写引擎；放大自博弈与 league；加对手配置预测头。
5. **M4 决策时搜索**：信念采样 + 搜索 + 根节点求解，对比无搜索版本的增益。
6. **M5 组队**（队伍生成/元博弈；前面阶段不重点做，待对战 agent 足够强后推进）；最终以受控的少量天梯局做外部验证。

## 7. 风险

| 风险 | 说明 / 缓解 |
|---|---|
| 吞吐不足 | poke-env 路径可能只有数百步/秒；尽早实测，必要时走 D2 的 b/c |
| 自写引擎不保真 | 机制极多；必须做整局 + 决策点 + 伤害用例的一致性验证 |
| 自博弈循环 / 可被利用 | 队伍相克有非传递环；用 KL 正则、league、利用者监控 |
| 评测噪声 | 局数不足会得出错误结论；固定队伍池、互换座位、报置信区间 |
| 数据过期（VGC） | 规则每季度变动；暂缓 VGC |
| sim-to-real / sim2sim 差距 | 训练与部署共用观测编码；定期用真实服务器回归 |
| 许可 / 规则 | Metamon 数据非商用；Foul Play GPL；Showdown 天梯对 bot 的态度模糊 |
| 目标可能超出范围 | 顶尖闭源 bot 靠的是数月开发 + 自写引擎；需合理设定阶段性目标 |
