# Differential testing of poke-engine against Showdown

The search uses poke-engine (Rust, `rust/patches/poke-engine-0.0.48`, patched by us) as its transition model; the referee of a game is Showdown's simulator (`vendor/pokemon-showdown`). Wherever the two disagree, the search is making decisions on a wrong model. The goal of this work: with full information, make the engine's prediction for every turn match Showdown's actual result field by field.

## Conclusion (2026-10-18)

- **Full match**: 71 random-battle differential datasets, **3,459,513** comparable turns in all (including turns that stop at a decision point); one of the engine's branches always matches Showdown's next state exactly, **0 mismatches**. Every dataset's baseline is empty, so any mismatch that appears from now on is flagged as new right away.
- 230 fixes in all (L1–L230, see the issue table in the appendix). The engine changes are in `rust/patches/poke-engine-0.0.48`; each one carries a comment `alpha-poke patch (date, doc/engine-diff.md Lx)` that points back to its entry in the appendix.
- Tests: `tests/test_dual_engine.py` has 1,028 cases (446 test functions); 1,180 tests in all; poke-engine's own tests: 229.
- What is not done yet: see "Known limitations" at the end.

## Method

### Main method: the full-information random-battle diff ("method 0" in the script comments)

- **How it compares**: `scripts/check_engine_random.py` (runner `enginecheck/random_battle.js`) plays fixed team pairs with fixed seeds in Showdown's simulator, both sides picking random legal choices. At every decision point it exports the simulator's full internal state. For each turn it builds the engine position from the values Showdown itself computed (`enginecheck.engine_state`) and compares all of the engine's branches for the same pair of choices against Showdown's next state (`closest(hp=True, full=True)`). The comparison covers everything a player can see: HP, status, stat stages, volatiles, terrain / weather / screens / hazards, items and last_item, PP, last move, available moves, tera state, times_attacked, etc.
- **Randomness is not a mismatch**: accuracy, critical hits, secondary effects and the order on a speed tie are all enumerated as branches by the engine; it is enough for one branch to match. Damage is aligned with hints the harness reads from the log (`damage_hints` / `roll_hints` / `move_hints`: single-hit damage, each hit of a multi-hit move, substitute share / break, crit +16384, KO +8192). The engine takes a hint only when it is exactly one of its own 16 damage rolls; the search never sets hints.
- **Determinism and baselines**: games are fully deterministic, so every position has a stable id `b<game>-t<turn>`. Every dataset has a baseline `tests/fixtures/engine_random_baseline_<set>.json`; after every fix each set's mismatches must be a subset of its baseline. Any (id, category) outside the baseline counts as a regression and the script exits with failure. Only after the subset is confirmed is the baseline updated with `--update-baseline --from-report` (without replaying the games).
- **Datasets**:
  - 41 regular ones, `scripts/check_engine_random_sets.sh`: main, seed10k, offmeta, random, wide, wide2, wide200, forum (OU team pools), randbats, randbats2–33 (random-battle teams generated by `scripts/randbats_teams.py`).
  - 30 big ones, `scripts/check_engine_random_big.sh`: big0–big29, 2900 pairs each. The teams are generated with fixed seeds into `data/teams/big/`, not committed; `BIG_SETS="..."` runs only some of them.
- **State construction is tested separately**: our own `build_state` (rebuilding the position from the protocol a player receives) is not part of this diff; for the separate state-construction diff see `doc/state-diff.md` (since 2026-10-23; before that this step had only scattered unit tests).

### Confirmation: dual-engine unit tests

The diff only gives leads; conclusions must come from `tests/test_dual_engine.py`. For each issue, write the test first and confirm it fails on the old engine; once fixed, it becomes a regression test. The tests are written in three ways:

- build a concrete scenario with `run_showdown` and run it on both sides;
- reproduce a position from the diff directly: `_random_position` / `_big_position`; the big datasets' team pairs are in `tests/fixtures/random_battle_pairs_big_l22x.jsonl`;
- assert with `alpha_search.damage_rolls` that Showdown's damage is exactly one of the engine's 16 damage rolls.

Control tests make sure the framework itself judges correctly.

### Auxiliary

- **Damage formula diff**: `scripts/check_damage_calc.py`; at the start of every turn it compares the top-roll damage of each move between Showdown's `getDamage` and the engine.
- **Data table tests**: `tests/test_engine_data.py`, comparing the move, Pokémon and item data tables.
- **Earlier method (retired)**: the self-play log diff (`scripts/check_engine_diff.py` (deleted 2026-10-28) / `explain_engine_diff.py` (deleted 2026-10-28)). It stitched the two sides' views together, so things like the opponent's remaining weather turns could only be guessed, and the positions were built by the code of the time. It did not compare with full information, and its results mixed issues from three sources: the engine, state construction and the method.

### Procedure (every entry goes through it)

1. Find the position in the diff, read Showdown's `sim/` and `data/` source, and work out the mechanism.
2. Write a dual-engine test and confirm it fails on the old engine (`git stash push rust src/alpha_poke`, touch, run the test, then `git stash pop`, touch again).
3. Port Showdown's shared mechanism instead of patching the single case, and name the entry id in a code comment.
4. Regression check: cargo, all of pytest, the 41 regular sets and the 30 big sets, each of which must be a subset of its baseline.
5. Update the baselines, add a row to the issue table in the appendix, commit.

## Lessons

1. **The diff must be full-information, deterministic and reproducible.** The self-play log diff stalled at about 93%, because stitching the views together and state construction mixed noise into the results. After switching to the simulator's internal state plus fixed seeds, every mismatch could be reproduced exactly, and only then did the baseline-subset rule hold.
2. **The diff's categories are only leads.** At first every "the engine has it, reality does not" was guessed to be something state construction failed to read; once dual-engine tests separated them, two of three turned out to be engine issues. Always write the test first and see it fail on the old engine first.
3. **Port the mechanism, do not fix the single case.** Most issues come down to a few of Showdown's shared rules that the engine did not copy:
   - **When Update runs**: after every hit of the hit loop; after an action ends; not between residual stages. This decides the timing of Berries, Harvest, and the order of Spikes and Berries on a switch.
   - **The BeforeMove priority chain**: sleep / freeze → Truant → flinch → Disable → Heal Block → Taunt. This decides whether PP is deducted and how the last move and the lock change.
   - **The order of onDamagingHit and onAfterMoveSecondary**: Berserk and Anger Shell are on the latter, after secondary effects.
   - **Residuals sorted by the holder's speed**: the holder of a slot condition is the target, so Future Sight resolves at the target's speed.
   - **The lifetime of activeMove**: Mold Breaker lasts until the drag-in, so a dragged-in Levitate still takes Spikes damage.
   - **runMove keeps the original priority when the move is changed**: a priority move forced by Encore is not blocked by Psychic Terrain.

   Read `sim/battle.ts` and `battle-actions.ts` first, then change the engine. One port often fixes several positions that looked unrelated.
4. **The harness must be as strict as the engine.** A good share of the "engine errors" were really problems in the harness's mapping or in its definition of the comparison:
   - the definition of typechange;
   - a Focus Sash removed by Knock Off was treated as having blocked the damage;
   - Dragon Darts has no `-hitcount`, so the substitute hint was not generated;
   - input-only flags (statsraised, illusion, notera, etc.) must not be compared;
   - Showdown and the engine count in opposite directions (turns remaining vs turns passed).

   Harness changes also go through tests and regression checks.
5. **The regression check must run in full, even when the target positions all match already.** After all 69 target positions of L228 were fixed, the full regression check caught another 425 issues introduced by this round itself: relaxing the release of the Choice lock wrongly affected cases with Disable. Be especially careful when relying on engine state that is "not always tracked": `State::use_last_used_move` is only on when needed, so the last move is not a reliable basis; decide the lock from the moves' disabled flags instead.
6. **Recall comes from scale and diversity.** After reaching 100%, every ~1 million new turns still found 70–160 new rare interactions (a first-pass match rate above 99.98%, but not 100%). Random-battle teams (randbats) cover far more moves and abilities than the OU team pools. Validation sets must be many batches, each with its own baseline; fixing against a single set is overfitting.
7. **Average damage and tolerances hide small errors.** An 8.5% HP tolerance cannot detect 1–3% formula differences, and crit branches can also "hit" the right answer by accident. Only after switching to Showdown's integer rounding with the exact 16 damage rolls, and aligning hit by hit with the log hints, did it really match point by point.
8. **Engineering pitfalls**:
   - Data must be streamed, and every run gets a memory cap with `systemd-run --user --scope -p MemoryMax=...` (on 2026-10-16 reading all the data at once crashed WSL).
   - Multiprocessing uses spawn, not fork (fork inherits the extension module's locks and deadlocks).
   - A panic in the binding is a BaseException and must be caught.
   - `uv sync` needs `--all-groups`, otherwise it uninstalls torch.
   - Touch after restoring from a stash / .bak, otherwise uv uses the old engine build.
   - Do not change Rust or the harness while a regression check is running: uv rebuilds midway, and the later datasets run on a half-new, half-old engine.

9. **The effect on real play is limited, but not zero.** With the same network and the same search, comparing the old and new engines on 5,288 self-play positions (doc/results.md "The effect of engine accuracy on decisions"): top-choice flips beyond search noise are 2.7%; measured by a 16,000-iteration reference search, each decision loses about 0.07% more win probability, concentrated in about 1% of critical positions. A battle A/B (1,200 pairs, the same network, only the engine swapped) measured the new engine at **52.38% ± 1.70%, i.e. +16.5 Elo** (interval +4.7 to +28.4): multi-step errors add up, but are not amplified to another order of magnitude. This is the gain of swapping the engine under a fixed network; the network may have adapted to the old engine's biases (which would make it low), but it cannot be taken as a strict lower bound. The 800-iteration search itself loses about 0.5%, about 7 times the engine error. "86% per-turn match" sounds bad, but most mismatches do not change the decision. The real bottlenecks are the search budget, the network's quality, and whether the position passed to the engine is accurate: fixing positions once brought +43 Elo.

10. **The diff cannot detect "corrupting the state in place while generating branches".** The diff rebuilds the state every turn, so a leak where the engine changes a field directly while generating branches without a matching instruction (so it cannot be reverted) is never visible in the diff; the search, however, generates and reverts repeatedly on the same state, and the leak stays in its world (L229: a leak of the saved move; in 51 / 1,200 games the search crashed and fell back to the heuristic). The added check: advance randomly from real positions and assert at every step "the state serializes the same before and after generation, and both sides have options" (`fuzz_generation` in `ismcts.rs`, `--ignored`, about 110k steps). Also, in battle summaries look at `search_fallbacks_a/b`, not `fallbacks_a/b`.

11. **The diff also cannot verify "a second copy of the rules written after the engine".** The network input (`extra.rs`) used to copy the engine's speed, end-of-turn and entry-hazard rules; the engine later fixed L24, L154, L211, L226 and L227, and the copy did not keep up. The features also borrowed the fixed-damage branch of `calculate_damage_rolls` from the engine; that path is not on the state transition and was itself wrong (L230), the damage diff happened to exclude Endeavor, and Pain Split is a status move, so it never enters the probe. The feature tests only compared the optimized version against the reference version, and both were wrong together. Combined conclusions such as "2HKO", "who moves first" and "answers" were never compared against actual results. What we do (2026-10-20): every rule calls the engine (the public `get_effective_speed` etc.; executed on a working copy, then undone with `reverse_instructions`); a feature's conclusions are treated as assertions and checked with engine transitions under the feature's own assumptions (`scripts/check_feature_claims.py`; the engine switch `set_no_chance`: no critical hits, no misses, no full paralysis / confusion self-hits, chance secondary effects do not happen; off by default); new calculations come with unit tests checked against Showdown (`tests/test_feature_claims.py`).

## Known limitations and follow-ups

- Not yet implemented in the engine: Belch (needs the "ate a Berry this battle" state). In real play `build_state` does not pass last_item yet (a Berry eaten by our own side can be inferred from the protocol).
- When the root in real play picks a replacement after our pivot move, `build_state` does not set the opponent's pending move (the engine's saved move); at that step the opponent is treated as not moving.
- The diff covers only Gen 9 singles with full information. The incomplete information in real play (the opponent's items, weather-extending items etc. must be inferred from the belief) is a matter for state construction and the belief model, not this document.
- The harness's roll hints are only used in the diff. The search still uses the engine's own branches: the exact 16 rolls near a KO, average damage otherwise.
- To push recall further: add more big sets to `check_engine_random_big.sh` (seed rule 3000000 + 100000k, offset 1000000 + 10000k), or generate new random-team sets.
