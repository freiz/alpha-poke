## 1. 目标与约束

**目标**：Gen9 OU 单打的强力对战 AI，水平接近或超越人类 pro；本地训练与评测（Python + uv + poke-env + 本地 Showdown，搜索与推理在自有 Rust crate）。研究方向：**隐藏信息有机地融入搜索**（不只是"采样后各搜各的"，D14）。原来的另一个方向"LLM 产生 MCTS 可用的先验"已结束：LLM 开局计划在首发和根节点先验两种用法上都没有可测价值（D11），代码已删除。

**非目标**：每回合调用 LLM 的在线策略（R§8.4）；双打 / VGC；其他世代。组队在计划内但不是当前重点（D5）。

**约束**
- 服务器：评测和训练只用本地 Showdown（`alpha_poke.servers.local_server` 只允许本机地址）。唯一例外是 `scripts/play_public.py --public`，只接受白名单对手的挑战，不上天梯、不进房间、不主动挑战。公共天梯只用于最终评测，原则见 D7。
- 许可：Foul Play 为 GPL-3.0，只作为外部进程对手，不 import、不复制代码；poke-engine（MIT）作为库依赖（vendored，一处改动，D2）；Metamon 数据集 CC-BY-NC-4.0，Metamon 原始 replay 只用于本地研究、不再分发。
- 密钥在 `.env`（公共服务器账号），不打印、不入库。

## 2. 问题特性

双人零和、**不完全信息**（对手配置隐藏，队伍预览只见 6 只物种）、**同时出招**（每回合约 9×9 的矩阵博弈，最优解常是混合策略）、随机性大（伤害浮动、会心、命中）、长时程（几十到上百回合）。没有 OTS：招式、道具、特性、太晶在对局中逐步暴露，努力值 / 性格永不可见。因此对手配置的信念模型和"怎么在搜索里用它"是核心问题。

## 3. 当前系统

```
poke-env（协议、局面跟踪）──► SearchPlayer（Python 薄适配层）
                                 │ 信念模型采样 N=32 个对方配置（整队条件先验 × 套路，β=1）
                                 ▼
                        alpha_search（Rust，释放 GIL）
                        SO-ISMCTS：一棵树、每次迭代换一个世界、开环随机
                        PUCT：双方先验 = 策略网络（对方用翻转视角前向）
                        叶子：价值网络（残差：手写评估的线性项 + 网络）
                                 │ 我方根访问分布
                                 ▼
                        指令；任何失败 → KnowledgePlayer 的启发式决策
开局：KnowledgePlayer 的规则计划只决定首发
```

- **网络**：Transformer（v5-glu 结构，D13）。人类数据训练的 `v5-glu` 之后进入自对弈（D15），**当前网络**记在 `data/selfplay/state.json` 的 `current`（2026-10-08：`sp-gen1-lr4e-4-p3-v1`，对 sp-gen1 56.5% ± 6.6%）。
- **对战配置**：`s_ismcts_glu`（CPU，Rust 推理）/ `s_ismcts_glug`（GPU 树并行）；`s_ismcts_ma` / `mb` 用运行时指定的网络（自对弈的代际比较）。`play_public.py`：easy = 启发式，normal = ISMCTS + v5-glu 200 ms，hard = 1 s × 4 线程。
- **自对弈**：`scripts/selfplay.py loop` 连续多代运行（D15）。

## 4. 设计决策

### D1. 目标赛制 —— 已定

Gen9 OU 单打。随机对战不需要组队，人类水平被拉低，不足以衡量 pro 水平；Gen9 OU 人口最大，也没有公开的顶尖 RL agent。

### D2. 基础设施 —— 已定

- **对战环境**：poke-env + 多个本地 Showdown 服务器，训练、自对弈和评测共用一条路径。本机约 3.8k 回合/秒，不含网络推理（`results.md`）。单个服务器上限约 1.3k 回合/秒。
- **前向模型**：poke-engine 0.0.48（`gen9` + `terastallization`）。搜索中当作近似模型，不作为训练真值。vendored 在 `rust/patches/poke-engine-0.0.48/`（`[patch.crates-io]`），唯一改动是 `before_move` 改为 `pub`（原地伤害计算，D15）。
- **自写快引擎暂不做**：等自对弈规模需要 10^8 局、Showdown 吞吐成为瓶颈时，再按实测决定。
- **Python / Rust 分工**：
  - Rust（`rust/alpha_search`，pyo3 + maturin，uv 本地包，改 Rust 代码后 `uv run` 会自动重编）：每步决策里反复跑的计算，即搜索、特征化、网络推理。
  - Python：协议、局面跟踪、信念采样（每个世界约 1 ms，其时间从搜索预算中扣除）、训练、评测、分析。
  - 接口是粗粒度的：每步调用一次，传局面字符串和 numpy 缓冲区。Rust 的 panic 在 Python 侧转成异常，然后退回启发式。
- **整体改用 Rust 的时机**：自对弈需要上百万局、poke-env 成为瓶颈时。

### D3. 算法路线 —— 已定

- **AlphaZero 式**：信息集 MCTS（D12）+ 策略 / 价值网络（D13），expert iteration 自对弈（D15）。
- **不用 alpha-beta + NNUE**：同时出招的最优解常是混合策略，期望节点让剪枝失效，而且两者都以完全信息为前提。搜索的主要开销在展开回合，而不在评估。
- **训练顺序**：先人类数据（行为克隆 + 胜负），再自对弈，不从零开始。理由：算力差距大；从零开始容易收敛到"对付自己"的打法；最终对手是人类，人类数据能直接教会"对手会怎么出招"。
- **LLM 不进决策**（D11）。

### D4. 复用 vs 自研 —— 已定

- 核心栈自研。
- Metamon 和 Foul Play 作为基线与评测对手：Foul Play 已接入（`scripts/vs_foulplay.py`，自对弈的外部锚点见 D15-6）；Metamon checkpoint 待接入，需要独立 venv 和 flash-attn。
- 复用 Metamon 的数据，不复用它的代码。
- 信念推断规则 clean-room 重写，不使用 `data.foulplay.cc`。

### D5. 组队 —— 已定：先用人类队伍，组队学习放到 M5

**评测**：40 支队伍的固定池（`data/teams/pools/replay40`），用配对赛程。"heldout" 指信念模型的训练数据里不含池中队伍。

**自对弈的组队（现行，`selfplay/teams.py`）**：目标是无偏地覆盖线上流行组队。
- 从 Metamon / 自爬 replay 里**抽一局真实对局，用这局里双方各自的队伍**：抽样分布就是天梯的实际分布；成对地抽保留了"同一分数段的队伍相遇"的相关性。按最近使用加权（半衰期 120 天，2025-05 以后）。这局的分数只用来抽队。
- 未暴露的配置用信念模型补全，补全后用本地 Showdown 校验器检查合法性（被禁的招式从校验器的提示里学到、去掉重抽）；没有信念数据的物种用 Smogon 统计补招式。
- 每对队伍只打一局（两边是同一个 bot，交换座位没有意义）。
- **补全和推断用同一个信念模型会让对手"太好猜"**：自对弈里对手的配置正好服从 bot 自己相信的分布，网络在"对手很好猜"的世界里学习，到真人对局会过于自信。缓解：
  1. **补全时更分散**：采样温度 1.3（每次抽取的权重 ^(1/1.3)；`temp = 1` 与搜索完全相同，已验证）；努力值按 Smogon 分布（温度 1，拉平会抽出长尾里的怪配置）。
  2. **混入完整的真实队伍**：30% 的一方换成目录里的完整队伍（D5-T），配置完全确定。
  3. 待做：补全用不同时段的数据拟合的信念模型；监控自对弈里信念对对手配置的命中率，和真人对局比较（D15-7）。
- 物种分布与来源一致；与 Smogon 最新统计的差距来自 Metamon 数据只到 2026-05（环境变化），要补新数据（TODO）。

**后期方向**：队伍元博弈（PSRO / double oracle）、以对战胜率为奖励的配置生成器（R§8.5）。

#### D5-T. 队伍数据

三类来源，只有第一类是玩家实际用过的完整配置：
1. **完整队伍目录**（`data/teams/catalog.jsonl`，入库）：Smogon 论坛帖子里的 pokepast.es 链接和直接贴出的 Showdown 导出（`teams/forum.py` 的 `SOURCES`：`sample` 议会挑选的样例、`teams_of_week`、`tour_bazaar` 比赛队伍、`rmt` 只取首帖）。每支队伍用本地 Showdown 转成规范导出（去掉昵称），按规范文本去重，**只保留今天的 gen9ou 规则下合法的**（规则变了以后从缓存重新 `build`，不用重新抓取）；`complete` = 6 只都有努力值、特性和 4 个招式。
2. **replay 重建的队伍池**（`teams/replay_pool.py`）：天梯上被照搬 ≥ 50 次的队伍，未暴露的部分用 Smogon 统计补。是近似。
3. **replay 和 Smogon 使用率统计**：只有暴露过的信息 / 边缘分布，用于信念模型（D8）。

数据布局（`data/teams`，说明见 `alpha_poke/teams/__init__.py`）：`raw/`（下载缓存）→ `catalog.jsonl` → `pools/<name>/`（`team_XX.txt` + `index.json`（文件名 → 预览物种键，heldout 信念模型据此排除）+ `meta.json`）。所有操作走 `scripts/teams.py`（`collect` / `build` / `stats` / `export` / `reconstruct`）。池：`forum_curated`（162 支真实完整配置）；`replay40`（默认评测池）/ `replay40b`（冻结不再重建）。heldout 信念模型按池缓存（`data/belief_model_heldout_<池名>.pkl`）。

#### D5-L. 精品队伍库与队伍排名（科研方向，未开始）

**两种用途分开**：训练和自对弈要覆盖整个环境；对战（上分、对特定对手）要的是很小的精品库（3–5 支轮换），可以专门针对它们自对弈 / 微调，冷门配置带来信息优势，代价是可被针对。

**队伍强度**定义为：我们的 bot 用这支队伍，对目标环境（按出现频率加权）的期望胜率。从便宜到贵的估计组成漏斗：replay 统计（按 6 只物种的胜率，逻辑回归扣掉分数差）→ 价值网络开局预评分（对抽样的对手队伍取平均）→ 模拟对战（逐轮淘汰）→ 元博弈（PSRO / double oracle）。候选来自目录 + 热门队伍、局部搜索（改招式 / 道具 / 太晶 / 努力值，校验器保证合法）。瓶颈是评估的局数。

#### D5-O. 针对特定对手的选队与打法（科研方向）

范围：只用公开数据（他上传的 replay）和我们与他的对局；只在 `play_public.py` 白名单内对战。对手的用户名不写进仓库，数据放 `data/players/<id>/`（git 忽略）。

**问题**：给定对手 o 的对局记录，选我们的队伍 C（以及打法），最大化对 o 的期望胜率，同时对他换队要稳健。

1. **对手的队伍分布 P_o(T)**：精确队伍（按最近使用加权）与风格（物种使用频率，用他那个分数段的天梯使用率做 Dirichlet 平滑，按队友共现补成 6 只）混合；参数用时间切分的似然来定。配置用个人化信念（每个物种的 Dirichlet 后验，先验是通用信念模型）。
2. **对手的打法模型 π_o**：网络的分数输入（Elo）和策略温度 τ 按最大似然拟合，不微调网络。
3. **候选队伍**：目录（合法 + 完整）、天梯热门队伍、局部改动；价值网络或对阵模型预筛。
4. **评估和选择**：对局按 P_o 抽对手队伍，配对比较；按显著性逐轮淘汰。稳健目标：按他的核心聚类，最大化均值减标准差或最差簇的胜率。
5. **对局中的利用**：搜索里对方用 π_o 的先验和个人化信念；每局之后更新。

**结果（2026-10-08，`results.md`）**：
- 按局数衰减最好（半衰期 2 局）：下一局 6 只里 70% 在模型前 10 名（天梯使用率 36%）。个人化配置比通用信念好，但只用他自己的数据更差，必须有先验。
- 拟合的分数输入就是他的真实分数（约 1100），τ ≈ 1.1，不比"真实分数、τ = 1"更好：网络的分数条件已经是好的打法模型。
- 选队：只用策略网络的对手太弱（我们的搜索 bot 对它约 99%），只适合粗筛；决赛双方都搜索。结论写进 `data/players/<id>/counter/`（`play_public.py --pool` / `--team` 直接加载）；`scripts/counter_pipeline.py <user>` 串起全部步骤。
- 他的数据：57 局，34 支队伍，换队频繁但核心稳定（Alomomola 77%、Kingambit 72%），P_o 的风格部分比精确队伍更重要。

### D6. 算力

- 本机：AMD 79xx（10 个逻辑核可用）、64 GB 内存、RTX 4070 Ti 12 GB。可以租云。
- 2026-10-08 起 WSL 给 20 个逻辑 CPU（10 个物理核）。修掉 PyTorch CPU 线程池的空转（GPU 路径只用 1 个 CPU 线程）后，自对弈约 5 万叶子/秒、约 2,000 局/小时，**瓶颈变成 GPU**（100%）；GPU 前向用 `torch.compile`（与不编译差 3e-6，每批快约 22%）。**自对弈期间不训练**：两者抢 GPU / CPU，吞吐会崩。
- 大内存任务一次只跑一个，用 `systemd-run --user --scope -p MemoryMax=...` 限制内存（曾经 OOM 导致 WSL 崩溃）。

### D7. 评测协议

- **配对赛程**：固定种子生成队伍对，每对交换队伍各打一局，双方轮流发起挑战，报配对胜率 ± 95% CI。成对分数的标准差约 0.335（五项分布：0 / ¼ / ½ / 1 约 16% / 2% / 52% / 30%），所以 100 对约 ±6.6 个百分点，检出 20 Elo 的差距要数百对。
- **每次 arena 运行都写 `<log>.meta.json`**：commit、`ALPHA_*` 环境变量、bot 定义和汇总。`results.md` 的表由 `scripts/results_table.py --write` 生成。arena 每局有 1 小时超时（2026-10-08：曾有 3 条对战线卡在第一局的挑战上）。
- **序贯检验**：`selfplay.py` 的评估用 fishtest 式 SPRT 提前停止（D15-6）。
- **降方差**：成对赛程降约 33% 的方差；运气校正（AIVAT 式控制变量，`scripts/luck.py`）离线只降约 12%，不接入（`results.md`）。
- **外部对手**：Foul Play（200 ms × 1 用于自对弈的定期检查，1000 ms × 4 作为强档）。
- **离线评测**：锚点验证集为上传时间 ≥ 1776921722 的对局（`--val-cutoff`）。种子标准差约为策略 CE 0.003、价值 BCE 0.0025，单次运行 0.005 以下的差别不可信。
- **公共天梯**：只用于最终 checkpoint，用新开的、明确命名的账号，最多几百局，报 Glicko / GXE。

### D8. 对手信念模型

- **现行**：`belief/priors.py`。
  - 整队条件先验：认出被照搬的队伍 → 核心条件 → 物种分布，逐级回退。
  - 招式 = 物种套路后验 × 整队条件边缘^β，β=1（`ALPHA_MOVE_BETA`）。
  - 模型用 5 万局自爬 replay 构建，评测用 heldout 版。
- **有效结论**（离线数字见 `belief_prior_eval.md`、`results.md`）：
  - 整队条件先验明显优于 Smogon 边缘分布，道具 top-1 为 76.6% 对 55.4%。
  - β=1 把采样招式对之后暴露招式的覆盖率从 61.7% 提到 77.3%。
  - "上场 t 次还没用某招"这种负证据几乎没有增益，没有接入搜索。
  - 对手实际招式不在世界里的约 21% **全部是对手之前没用过、信念也没猜中的招式**，不是 bug；改进要靠信念（D14-3）和 32 个世界的合集覆盖。
- **短板**：招式不确定性。完全信息的价值几乎全在招式上（D11）。

### D11. 隐藏信息与 LLM 先验：已有结论

- **完全信息的上界**：知道对方真实配置约 +8–12 个百分点，几乎全部来自招式（只给招式 57.5%；道具、太晶、努力值都不显著）。
- **确定化（K 份世界各搜各的）的内在矛盾**：世界的多样性和每棵树的深度争同一份预算，K=4–8 最优。这是改用 ISMCTS 的直接动机。ISMCTS 对确定化 57.3%。
- **LLM 开局计划没有可测价值**：启发式 bot 上对规则计划 51%；搜索 bot 上 LLM 首发 47%，计划作根节点先验 47%。根节点后处理太浅，计划要起作用必须进入树内。方向已结束，代码已删除。

### D12. ISMCTS（`rust/alpha_search/src/ismcts.rs`、`bsearch.rs`）—— 现行

- **SO-ISMCTS**：
  - 一棵树建在我方信息集上，每次迭代轮换一个世界，在该世界的根局面上原地 apply / reverse。
  - 子节点的键是（我方行动标签, 对方行动标签）。对方招式按招式 id，换人按队伍位置，跨世界一致。
  - 选择用双方解耦的**可用性** UCB / PUCT：每个行动单独记录"可用次数"。
- **开环随机**：与单世界的 poke-engine MCTS 持平；前 2 层闭环无提升。
- **只缓存根节点的指令表**：开环下同一节点在同一世界里会以不同局面到达，而 poke-engine 的指令带绝对值。
- **PUCT**：`Q + c·P·√N/(1+n)`，FPU 取已访问分支 Q 的均值。我方先验来自叶子的那次前向；对方先验来自翻转视角的前向；只在后来的世界里出现的对方选项用均匀先验。搜索中要**价值和先验一起用**：先验约 +70 Elo，价值约 +47 Elo；只用价值时更弱。
- **CPU**：根并行，`threads` 个独立的树，最后合并根统计；4 线程约 3.75 倍。
- **GPU**（`bsearch.rs` + `agents/gpu_net.py` + `agents/gpu_search.py`）：**树并行**，8 个线程同时下降同一棵树（virtual loss），批量 32，流水线（GPU 算这一批时 CPU 收集下一批）。同样 0.5 秒，与深搜索的首选一致率约 70–75%（CPU 单线程 65%）；多棵独立的树没有用。
- **自对弈**：许多局的搜索共享一个批量线程（`collect_many` / `apply_many`，D15-2）。
- **决策**：选我方根访问数最多的行动（自对弈按访问分布采样）。
- **已知局限**：
  - 对方在树中按"看穿我方全部配置"出招（D14-1）。
  - 对方的统计跨世界平均（反向的策略融合）；正解是 MO-ISMCTS。
  - 树内不更新信念（D14-3）。
  - 搜索对搜索偶尔陷入无限换人的拖延循环（自对弈有 300 回合上限）。
  - 复活祝福无法表示，会退回启发式，约每 100 局 1–2 次。

### D13. 策略 / 价值网络与训练 —— 现行

**人类训练数据**：Metamon 原始 replay 里的 Gen9 OU 2,038,375 局（`data/metamon/gen9ou`），加上自爬 5 万局（只用于信念模型和评测）。
- `alpha_poke/train/positions.py`：逐行回放 replay，为抽中的决策点建单方视角的 poke-engine 局面。己方用整局暴露的信息加信念补全，招式顺序打乱；对方只用当时已暴露的信息加信念。用 `scripts/build_training_data.py` 构建（流式、可断点续跑、heldout 信念；`PYTHONHASHSEED=0` 可复现）。
- **决策步**与 poke-engine 的决策节点一一对应：回合开始、U-turn 等招式后的换人、倒下后的强制换人；看不到动作的回合（被阻止 / 行动前倒下）用部分标签（"某个招式槽"）。每局从全部决策点合成的池里统一抽 20 个（`--pool all`），各类比例与真实对局一致，不需要权重。
- 列：实际行动（14 槽）、胜负、`history`（最近 8 个决策步）、`future`（之后 4 步双方的动作，MTP 标签）、公开信息标记、双方赛前分数、对手整局最终暴露的配置（辅助头标签）。

**特征**（Rust `features.rs` + `extra.rs`，训练与搜索共用）：
- 12 个实体（稀疏 id：物种 / 道具 / 特性 / 太晶 / 属性 / 4 招 + 稠密特征）、全局特征、14 槽合法动作掩码、8 步历史。
- 每只宝可梦的公开信息标记（对手的 = 我们看到的；我方的 = 对手看到的）；回合数、天气 / 场地剩余回合、存活数、总 HP 等数值；招式静态属性表。
- **对阵计算**（poke-engine 的伤害计算）：双方在场的伤害比例与击倒线、谁先动、后备挨对方最有效一招的伤害与反打能力、入场钉子伤害。**收益最大的一组**（策略 CE −0.05）：击倒线、先后手这类"乘法加阈值"的计算网络很难自己学出来。原地计算（D15-3）后每个局面约 5 µs。
- 双方赛前分数（标准化、分差、是否已知；训练时随机遮成"未知"）：校准变好。

**模型**（`train/model.py` 的 `TransformerPV`，`scripts/train_pv.py`）：
- 12 个实体 token + 1 个全局 token + 8 个历史 token，pre-norm 3 层，d = 128，4 头；**v5-glu 结构**：SwiGLU 前馈（中间维度 171）+ RMSNorm + QK-norm，73.7 万参数。价值头和策略头读全局 token，换人槽读己方实体 token。价值是残差：`logit = a·eval/100 + b + net`。
- 辅助输出：MTP-3（之后 3 步双方的动作，权重 0.5、按步衰减 0.5^k）、对手配置头。
- 人类数据上的 v5-glu（`data/train/v5/runs/v5-glu`，sha256 前缀 `1bdb84317007011a`）：对 v5-final（ReLU、LayerNorm）策略 CE −0.008、价值 BCE −0.003，训练慢 8%，Rust 搜索的叶子速度相同。`baseline-v5`（git tag）是结构实验前的版本。

**有效结论**（数字见 `results.md`）：
- 历史与 Transformer 叠加的效果大于各自之和；历史长度到 8 步饱和。
- MTP-3：价值 BCE −0.0056，换人 CE −0.026，主策略不变；它不能替代翻转视角的对手先验（预测对手动作 43.6% 对 48.6%）。
- 历史步的结果（伤害、会心、先后手）没有可测效果，不用。
- 结构：只有 glu 稳定变好；去掉 QK-norm 提升变小、训练不稳定；深而窄无差别；smolgen 更差（价值更早过拟合）。原则：**推理不能系统性变慢**，否则等于浪费了"原结构 + 更多参数"的机会。
- 信念样本对网络没有额外信息：对手未暴露的字段遮成"未知"后策略、价值不变，对手配置头反而略准（见 D14-3）。
- 价值头受数据量限制（10% 数据时所有改动都不灵敏），而且容易过拟合同一局的胜负（D15-5）。

**推理**：
- **Rust CPU**（`tnet.rs`）：逐层对应 PyTorch；AVX-512 寄存器分块的矩阵乘法，SwiGLU 补零到 16 的倍数，silu 的 exp 用多项式（AVX-512 与标量逐位相同）；单线程前向约 207 µs。一致性检查 `scripts/check_tnet.py`（1e-5 量级，argmax 100% 一致），**每次修改推理代码都要重跑**；伤害特征的原地计算用 `scripts/check_extra.py` 逐位对照。
- **搜索中的上下文**：每个世界一个（真实历史、公开信息标记、双方分数、回合数），由 `agents/net_context.py` 用与训练数据相同的函数构造；树中下降时，路径上的动作加进历史，用过的招式 / 太晶 / 换上的宝可梦标为已暴露。
- **GPU**（`agents/gpu_net.py`）：同一个 PyTorch 模型，CUDA Graph 按固定批量录制，与 Rust 推理在同一批叶子上误差约 1e-5。

### D15. 自对弈 pipeline（expert iteration）—— 现行

目标：搜索 + 网络自对弈产生训练目标（根节点访问分布、胜负），训练出更强的网络，循环。入口：`scripts/selfplay.py`（`teams` / `run` / `value` / `convert` / `train` / `eval` / `baseline` / `foulplay` / `cycle` / `loop`），代码在 `alpha_poke/selfplay/`。

**重新开始（2026-10-09）**：第一轮（gen0–3，2026-10-08）有几处数据和评估问题：各代组队种子相同（对阵约 5,000 组反复出现）、训练种子相同（人类锚数据每代是同几个分片）、前几次晋升在 40 队池 + CPU 500 ms 下判定（该池会误判）。在新标准（宽池新队伍对、3,000 次迭代）下，sp-gen3 对 sp-gen0 是 48.1% ± 2.9%，四代没有可测的进步。所以从 v5-glu 重新开始，Elo 锚点改为 v5-glu = 1500；旧数据、模型、状态归档在 `data/archive-2026-10-08/`，旧登记在 `exp/archive-2026-10-08/`。累计检查的回滚只在显著更弱（LLR 越过下界）时发生，打满未决算停滞；第 0 代不做累计检查。

**1. 对局在本地 Showdown（poke-env）上跑**，不用 poke-engine 直接对打：poke-engine 只是搜索里的近似模型，用它当真值会把它的误差学进网络；Showdown 的吞吐不是瓶颈。

**2. 搜索和推理**（`selfplay/runner.py`、`batcher.py`、`player.py`）：
- 4 个进程 × 每进程 24 局同时进行；每个进程一个批量线程，所有等待中的搜索每轮各取几个叶子合成一批（最多 512 个叶子），一次 GPU 前向，流水线；`choose_move` 是异步的，等搜索时其他对局照常进行。约 3.6 万叶子/秒、1,400–1,600 局/小时，CPU 已满。
- **搜索设置**（实测，`results.md`）：25% 的决策完整搜索并产出策略目标，其余快速搜索（16 个世界）只用来下棋。**2026-10-10 起（第 4 代）1,600 / 400 次**（之前 3,000 / 600）：每步平均约 700 次迭代（之前约 1,200），同样时间多约 1.7 倍对局；1,600 次的目标保留 3,000 次相对先验约八成的改进。原因：sp-gen2 对 sp-gen0 只用策略显著更强（52.4% ± 1.9%），在 3,000 次搜索下却无差别（49.3% ± 2.9%）——先验在进步，深搜索的强度取决于价值头，价值最缺的是独立对局（每局一个胜负）；根节点 Dirichlet 噪声双方 ε = 0.10、总浓度 10（ε 到 0.25 后目标变差）；实际下的招按访问分布采样：前 8 个回合 τ = 1（多样性），之后 τ = 0.25（访问数开 4 次方再抽，基本只在最接近的几招之间选；2026-10-08 起，第 3 代开始。之前全程 τ = 1：第 2 代只有 58% 的招是访问最多的那招，局面稳赢却因随机抽到次优招而输，会让胜负标签变成有噪声的价值目标；AlphaZero 前 30 步后直接选最多、KataGo 逐步降温）；只有一个合法选项时不搜索。
- 分数输入：bot 用"未知"（0），不给 bot 编造分数，避免污染"分数 r 的人怎么下"。
- 300 回合上限：认输结束，标记 capped，不给胜负标签。
- **内存**：循环的每一步（`cycle` 的各步、`baseline`、`foulplay`）都在 cgroup 内存上限下运行（`systemd-run --user --scope -p MemoryMax=40G`，`--mem-cap-gb`）：超出的那一步连同子进程被它自己的 cgroup 杀掉，不会耗尽整个 WSL（2026-10-09：一个 373 万局面的超大分片做特征时占到 41.5 GB，加上同时在跑的评估，WSL 的 48 GB 用尽，WSL 崩溃）。特征计算整片放在内存里（峰值约 21 KB/局面），`train_pv.MAX_SHARD_ROWS` = 120 万、`build_training_data --max-games` = 6 万局，超过即报错，先用 `scripts/split_shards.py` 切。大内存的任务不和评估 / 自对弈同时跑。
- 健壮性：引擎 panic 只让那一个搜索失败（Rust 里每个搜索 `catch_unwind`），该步用启发式；批量线程有兜底；每次等搜索最多 120 秒，每局最多 2 小时，超时后这条对战线换一对新玩家（旧玩家还挂着没下完的对局，之后每局都会等它；2026-10-09 第 1 代因此一条线卡死，58 局没下）；用户名每次运行带随机后缀（否则服务器会把上次没下完的对局交给新连接）。poke-env 跟踪不了的队伍（它按基础种类或名字里 "-" 分开的任一段认宝可梦，Porygon 和 Porygon-Z 会被当成同一只，队伍预览就报错、对局永远开始不了）在抽队和开跑前都会跳过（`teams.poke_env_clash`；第 1 代 1 万对里 1 对，评估宽池里没有）。
- **每代的对局必须由当前（晋升后的）网络下**：`run` 默认读 state.json 的 `current`，目录里已有别的网络下的对局则拒绝（第 0–2 代曾因默认值写死而全由 v5-glu 下）。

**3. 记录与转换**（`selfplay/convert.py`）：
- 每次决策由 Rust 直接记录（`BatchSearch.record()`）：**根节点网络输入**（世界 0 的局面 + 上下文，训练直接用它，和搜索看到的完全一致）、14 个槽位的访问 / 平均价值 / 先验 / 合法、根节点 q、选项名、对方的访问分布、是否完整搜索、实际下的招。
- 整局才知道的标签（胜负、MTP 的未来动作、对手配置等）由 replay 管线从对局日志得到，按（座位, 回合, 决策类型）与记录对齐（招式按名字核对，一致率 99.6%）。
- 训练数据与人类数据同列，多出 `pi`（访问分布）、`pi_w`（1 = 完整搜索）、`q`、`value_ok`（capped 的为 0），存 `data/train/sp<g>/`。

**4. 双方是谁**：当前网络对自己，双方相同设置。待做：一部分对局的对手是历代网络、一部分是"人类@分数"模型（`pol`），防止收敛到"对付自己"（D14-2）。

**5. 训练**（`selfplay.py train` → `train_pv.py --selfplay ... --init <当前网络>`）：
- 损失：策略对完整搜索局面的访问分布 π 做软交叉熵 −Σ π log p（人类的 one-hot 是特例）；价值 BCE；MTP、对手配置头照旧。
- **每局最多 50 个局面**（`--per-game` / `train_pv.py --sp-per-game`，2026-10-08）：带策略目标的（完整搜索）优先，其余随机，整个训练固定。第 2 代每局决策数中位 63、99% 分位 282、最长 648：约 2% 的长局（受队对受队的换人循环）占了 9% 的局面，全部使用等于加重了循环局面的权重；截到 50 后它们只占约 2%，普通对局的策略目标几乎全保留（中位每局 16 个）。训练步数按截断后的局面数算（`--sp-passes`）。
- 数据：最近 5 代的自对弈局面，加上更早各代按对局抽样（合计约为窗口的 20%，`--old-share`），再和人类数据按比例混进同一批。人类是"锚"（保持对人类对手的理解，等价于 piKL 正则），比例逐代降低：max(20%, 50% − 5% × 代数)；上一代人类验证集漂移超过警戒线时不再下调。人类数据每代只抽约 0.02 个 epoch。
- **更新幅度**（第 1 代同一数据重训对比，`results.md`）：lr 1e-4、2 遍时与起点的 KL 只有 0.002，太保守。策略随更新加大持续靠近搜索分布（搜索分布是多次 tryout 叠加的结果，比网络先验好）；价值（每局一个胜负，噪声大）约 1 遍后开始过拟合。默认 **lr 4e-4、3 遍**（每个自对弈局面平均被抽 3 次，均匀有放回）、20% 预热、余弦衰减；重训的第 1 代对原第 1 代 56.5% ± 6.6%。
- **价值目标**（进行中）：自对弈每局的全部局面共用一个胜负，约 74 个相关局面反复出现同一个标签（AlphaGo 论文里的过拟合）；原来"每局总权重 4"的加权被批内加权平均抵消，只起到"长局短局一样重"的作用。选项：
  - `--sp-value-passes k`：一个局面的胜负只在前 k 次被抽到时进价值损失（默认 1；只挽回一小部分）；
  - `--sp-value-per-game k`：每局固定随机取 k 个局面进价值损失；
  - `--sp-value-lambda λ`：λ 回报目标，局面 t 的目标 = (1 − λ)·下一步的根节点 q + λ·下一步的目标，终局是胜负（不同局面的目标不同、噪声更小；MuZero / KataGo 类）。
  - 第 2 代空档对比 k = 1、λ = 0.9，以第 2 代新对局上的价值 BCE 评判（D15-7）。
  - 若人类数据把价值学偏：价值加"数据来源"输入，或分成人类 / 自对弈两个价值头。
- 从当前网络热启动，每代继续训练，导出最后一步（`--export last`）。
- **随机种子按代**（2026-10-08 修）：组队抽样（`teams --seed <代>`；以前每代都是 0，第 1–3 代 99% 的来源对局相同，对阵组合只有约 5,000 种）、训练（`train_pv --seed <代>`；以前每代抽到同样几个人类数据分片作锚）、每条对战线的随机数（含本次运行的标签）。人类验证子集固定用种子 0 抽（各代可比）。
- **第 2 代没有提升（2026-10-08）**：sp-gen2 对当前网络 46.5% ± 4.0%（199 对，3,000 次迭代；约 −25 Elo，95% 区间约 [−53, +3]），不晋升；训练指标却都变好（自对弈 KL 0.282 → 0.272、价值 BCE 0.457 → 0.451）。排查：
  - 实现：评估加载的权重、Rust 与 PyTorch 一致（6e-6）、第 2 代数据的搜索设置、转换、每局 50 个的截断都没问题。顺带修了两个潜在 bug：GPU 自对弈（`load_run`）读 `best.pt` 而评估读导出的最后一步（`--export last` 时两者不同；对第 2 代没有影响，因为那个网络 best = last）；清理时删掉的 `eval_pv.py` 让 `check_tnet.py` 跑不了。
  - **策略在变平**（同一批局面、无噪声）：策略熵 v5-glu 1.19 → sp-gen0 1.25 → 当前 1.26 → sp-gen2 1.27，平均最大概率 0.553 → 0.529。猜想是搜索目标里带着探索造成的访问（KataGo 用 policy target pruning 剪掉）。**但实测剪枝只去掉 2.6% 的访问**，目标熵 1.04 → 1.01；而且网络的熵（约 1.26）本来就比目标（约 1.04）高：网络比它的目标更平，原因更可能是软目标的交叉熵是"覆盖式"的（网络预测不准搜索会集中在哪招，就在可能的招上平均），而不是目标太平。同时网络首选与搜索首选一致率在升（v5-glu 65% → 当前 70.5%），与目标的 KL 在降。所以剪枝预计作用很小；平坦化本身是否有害未定，作为监控指标跟踪（D15-7）。`selfplay/convert.prune_visits` 已实现，未接入训练。
  - 其他可能：统计噪声（区间包含 0）；窗口里三分之二的数据是 v5-glu 下的（第 0、1 代）；每代热启动时 AdamW 状态归零（人类漂移集中在前 130 步）。

**6. 评估、晋升与多代循环**（`selfplay.py eval` / `baseline` / `foulplay` / `loop`）：
- **队伍：每次评估新抽一批真实对局的队伍对**（2026-10-08 起；`eval_pool`，与自对弈同一个抽样器，种子 = 100,000 + 评估种子，与训练不重合；按真实的队伍对打，交换两边）。以前用 40 支被照搬的热门队伍（`replay40`，Smogon 标准配置补全）：同样是 sp-gen2 对 gen1，40 队池 46.5% ± 4.0%，200 组真实对局队伍对上 53.6% ± 3.8%（LLR 3.97，晋升）。小池只代表一小块、接近完全信息的分布，而且每次评估都从同样的 40 支里抽，系统性的偏差每代重复。
- **GPU 评估**（2026-10-08 起，默认）：和自对弈同一套跨对局批量搜索（每个进程两个批量器，一个网络一个；无根节点噪声，选访问最多的招，3,000 次迭代、32 个世界），4 进程 × 12 局。与 CPU 逐局搜索的首选一致率 88.8%，两次 CPU 搜索之间 90.0%（80 个局面），等价。100 对约 15–20 分钟（CPU 约 45 分钟）。`--no-gpu` 退回 CPU。
- **搜索量**：相邻两代结构相同、每个叶子的成本一样，评估按**固定迭代数**（`--iterations 3000`，与自对弈的完整搜索相同；2026-10-08 起，第 1 代及以前是固定 500 ms，约 1,500–1,800 次）。评估时 24 局挤在 10 个核上，500 ms 能做的迭代数随负载在 1,500–1,800 间波动，固定时间会给本来就很吵的胜率再加一层噪声，也不可复现。例外：对 Foul Play（按时间搜索）和网络扩容 / 换结构之后（每个叶子更贵）要按同等时间比。
- **每代规模**（2026-10-10 起，第 4 代）：**5 万局**（之前 1 万：单代进步约 5 Elo，400 对的评估测不出；更大的代让单代进步可测，总计算量不变；已抽的队伍不足时补抽，`teams --append`）。人类比例仍按代递减（每代 −5%，下限 20%）：按局数算会降得太快，而 `hce_unk` 已在逐代上升。
- **每代**：新网络对当前网络，配对，**SPRT**（`sequential_match`，fishtest 式，成对分数的正态近似）：H0 = 新网络弱 20 Elo，H1 = 持平，α = β = 0.05（LLR 界 ±2.94），每完成 12 对检验一次，越界即停，**晋升评估 1,600 次迭代、上限 600 对**（2026-10-10 起：更接近先验的进步、同样时间多打对数；每 3 代的累计检查保持 3,000 次、400 对，盯住深搜索下的实力。模型登记的 Elo 拟合目前把两种搜索量放在一起，待分开）。之前：上限 **400 对**（每 3 代的检查也是 400 对；2026-10-08 改：单场 Elo 95% 区间约 ±23，100 对时约 ±46；GPU 评估最长约 1 小时。之前：上限 100 对、检查 200 对；2026-10-08：200 对只把持平时的晋升概率从 0.67 提到 0.74、弱 20 Elo 时从 0.31 降到 0.27，却多花约 45 分钟，累计退化由每 3 代的检查兜底），打满时按 LLR 符号（平均分 ≥ 48.6% 晋升）。按 gen1 实测的成对分数分布模拟（`results.md` 的表）：真实平均分 0.47 / 0.50 / 0.53 时晋升概率 0.27 / 0.74 / 0.97，平均 190–200 对；只有差距很大时提前停。旧规则（100 对，p + CI ≥ 0.5）放过弱 50 Elo 的候选的概率约 1/3，多代下来会慢慢变弱。
- **每 3 代**（`baseline`）：当前网络对 3 代之前那代结束时的网络（state.json `lineage`），同一 SPRT；判"更弱"则回滚到它并停下；没有显著进步（p − CI ≤ 0.5，或 3 代没有晋升）记一次停滞，**连续 2 次停滞就停下等人看**：先区分原因再扩容（训练和验证的 KL 都降不下去 = 容量不够；KL 在降但棋力不涨 = 搜索目标到顶；价值太吵 = 价值目标）。固定的 v5-glu 在领先很多以后测不出退化，不再定期比。
- **每 9 代**（以及第一次，作为参考）：对 **Foul Play**（第三方，固定设置：我方 CPU ISMCTS 200 ms 单线程 vs Foul Play 200 ms × 1，heldout 信念，200 对，8 条线约 20–30 分钟）。不参与晋升；比同设置下的历史最好成绩低 5 个百分点以上且显著（z > 1.96）时停下等人看。用途：发现自对弈的循环 / 遗忘（只对自己的打法有效）。
- 不晋升：当前网络不变，被拒那代的数据留在窗口里。只有被拒的候选**变化大**（`sp_kl_ref` ≥ 0.01）时，下一代学习率减半（最多 1/8）、人类比例不下调；变化小的被拒视为评估噪声。连续 3 代不晋升：停下。
- **模型登记**（`exp/`，进 git；`selfplay/registry.py`，`selfplay.py registry` 重建，每次 eval / baseline / Foul Play 后自动更新）：`exp/matches.jsonl` 每场比较一行（双方、搜索方式与迭代数、队伍池、局数、成对胜率与 CI、LLR、结论、日志；`elo` 标记是否参与 Elo 拟合：正式的晋升 / 检查评估参与，诊断实验只记录）；`exp/models.json` 每个模型一条（权重哈希、父网络、代、训练设置、最后的验证指标、是否晋升、下过哪几代的自对弈、Elo 与 95% CI、相关比较）。Elo：**sp-gen0 固定为 1500**，各比较按成对胜率换算成 Elo 差、按其方差加权做最小二乘联合拟合。
- 失败的步骤重试一次（各步可以断点续跑）。记录：`data/selfplay/loop.log`、`state.json`（当前网络、`lineage`、每代的结果）、`gen<g>/summary.json`。

**7. 监控（每代报告）**：
- **价值头在新对局上的检查**（`selfplay.py value`，每代下完对局后、训练前，CPU 推理 3 万个决策，约 1 分钟）：这一代的对局对之前所有网络都是没见过的，是价值在"bot 对 bot"上的样本外测试。报告当前、前 1–2 代、v5-glu 的 BCE、ECE、校准斜率（> 1 = 过于保守）和相对当前网络的 BCE 差（按对局聚类的 95% CI）。第一次（gen2 前 1,713 局）：只学人类对局的 v5-glu 校准正常（斜率 0.98）但区分能力差 0.02，第 0 代混入自对弈即补上。
- **策略的平坦化与搜索目标**（同一步，2026-10-08 起）：各网络在这一代新对局上的策略熵、平均最大概率、与完整搜索目标的 KL 和首选一致率；目标本身的熵（原始 / 剪枝后）、剪枝去掉的访问比例、搜索相对它所用先验（含噪声）的 KL。网络越来越平而首选一致率不升，就说明平坦化在伤害搜索。
- **按队伍分组**（同一步的 `by_team`，2026-10-09 起）：按做决策一方自己的队伍分为队伍库整队（`catalog`，1,176 支固定配置，每代每支约用 5 次）、热门（6 只的组合在第 0 代到本代的队伍里出现 ≥ 10 次，`--popular`）、冷门（≤ 1 次，`--rare`）、中间；每组报告各网络的价值 BCE、相对 v5-glu 的提升（`gain_vs_base`）、策略与搜索目标的 KL / 首选一致率。用途：自对弈的队伍来自天梯分布，热门组合反复出现，队伍库的整队更是原样重复；如果几代之后热门 / 队伍库组的提升继续扩大而冷门组停滞，就是对常见队伍过拟合（评估池用同一个抽样器，测不出这一点）。第一次（第 1 代新对局，sp-gen0 样本外，6,000 个局面）：价值提升 队伍库 0.009 / 热门 0.013 / 中间 0.014 / 冷门 0.016，策略 KL 下降各组 0.075–0.088，没有过拟合迹象。
- **人类数据上的漂移**（`train_pv.py` 的 `evaluate_drift`）：人类局面上交叉熵变差本身是预期的，要防的是**忘记人类会怎么下**（搜索里对手的先验来自同一个网络）。`hce_true` / `hce_unk`（真实 / 未知分数输入下对人类所选招式的交叉熵，按分数段）、`kl_ref_*`（与训练起点的策略 KL）、`opp_act_acc`（预测对手下一步）。**护栏**：`hce_true` 变差超过 0.01 或 `opp_act_acc` 下降超过 1 个百分点 → 不再下调人类比例。
- 自对弈验证集（每代 5% 的对局）：`sp_kl`、`sp_top1`、`sp_bce`、`sp_kl_ref`。
- **对局统计**（`selfplay.py stats` / `selfplay/stats.py`，每代下完对局后，只读日志，几秒）：回合数（均值、中位、90 / 99% 分位、超过 100 / 200 回合、截断数）；出招构成（回复 / 保护、强化、所有变化类招式、换人的比例）；以上都**按双方队伍的防守程度分组**（两队的回复 / 保护 / 强化招式 + 再生力 / 毒疗之和，分 0–3 / 4–7 / 8–11 / 12–15 / 16+）；以及**队伍构成固定**（按上一代各组的比例加权）时平均回合数相对上一代的变化和 bootstrap 95% CI。用途：双受对局本来就长，同样的队伍构成下变长才说明打法更保守或在绕圈。

### D16. 自对弈的队伍分布 —— 研究中（2026-10-09）

**问题**：随机对战（Random Battle）的队伍由系统生成，训练分布就是比赛分布，和围棋类似；OU 的对手队伍来自玩家选择，高度集中在当前环境（Great Tusk 在 31% 的队伍里），而且队伍里有成套的配合（天气、钉子 / 清钉、强化 + 辅助）。完全随机组队学不到"对面是雨天队"这类知识；只按天梯分布抽，又可能对冷门组合、非常规配置不稳。现状（D15，`selfplay/teams.py`）：按时间加权抽真实对局、补全双方配置（70%），或整支换成队伍库的队伍（30%，1,176 支固定配置，每代每支约用 5 次）。两代 1.5 万对：来源对局几乎不重复，前 100 个组合占补全队伍的 11.5%。

**自对弈的抽队：多个来源混合**（比例待实验定）：
- A. **天梯真实队伍、压平热门度**（约 55%）：权重再乘 1 / 组合出现次数^β（β = 0 即现状，0.3–0.5：头部仍最多，但不再重复几十次）。
- B. **核心拆配**（约 20%）：从真实队伍里认出 2–3 只强相关的核心（Smogon 队友统计，`UsageStats.teammates`），保留核心，其余按"已选成员条件下的队友分布"逐只补全；过校验，再加简单的结构检查（清钉、速度控制等），太离谱的扔掉。保留配合，组合出没见过的队伍。
- C. **队伍库整队**（约 15%，现在 30%）：或每代每支最多用 1–2 次。
- D. **按使用率随机组队**（约 5–10%）：种类按 OU 使用率^α 抽（压平），配置由信念采样器补全；再留约 2% 给更冷门的种类。比例要小：这些队伍和信念模型的先验差得远，搜索对它们配置的猜测偏，策略目标噪声更大。
- 以后（M5，D5-L / D5-O）：双方不对称，我方从"打算带的队伍"里抽，对方从宽分布里抽。

**评估与训练分开**：训练分布可以比比赛宽（领域随机化），晋升只认要打的分布。
- **晋升评估保持天梯分布宽池**（D15-6）：测的是天梯实力；各代可比；混入随机队伍会让队伍强弱差盖住实力差，同样局数测出的更少。
- **诊断池**（固定队伍对，历次可比，不参与晋升；`selfplay/pools.py`，`scripts/team_pools.py`，`data/teams/pools/`）：
  - `offmeta200`：双方都偏门的真实对局（窗口内同组合 ≤ 2 场，且至少 4 只不在使用率前 40；符合的 11,037 场），补全方式同自对弈、不用队伍库；每队平均 4.94 只前 40 以外，427 个不同种类。
  - `random200`：按 OU 使用率^0.5 抽 6 个种类（使用率 ≥ 0.1%，同种限制，无队友结构），信念采样器补全；每队 3.25 只前 40 以外，234 个种类。
  - 参照：天梯池 `wide200` 每队 2.44 只前 40 以外，300 个种类。
- 每代的分组价值检查（D15-7 `by_team`）继续报告。

**判据**：多样化之后，天梯池的晋升评估不掉分、诊断池上涨 → 有效；天梯池掉分而诊断池涨 → 比例太大，往回收。严格的 A/B（两条分支各跑几代）代价太大，靠诊断指标看趋势。

**第 1 步（2026-10-09，完成，`results.md`）**：sp-gen1 对 v5-glu 天梯 / 偏门 / 随机池 54.6% / 51.6% / 51.8%（各约 ±4.3%），对 Foul Play 59.1% / 63.3% / 60.8%。自对弈的进步在天梯池最明显、另两个池约三分之一，但池间的差不显著；整体实力在偏门 / 随机队伍上没有变弱。**结论：多样性目前不是明显的短板**，不急着大改分布。下一步：先做改动小的 A（压平热门度，β = 0.3）和 C（队伍库 30% → 15%）；诊断池不进循环（每次约 1.5 小时，信息有限），需要时手动跑（`selfplay.py diag`：当前网络对 v5-glu，三个池），看天梯池与偏门 / 随机池的差是否随代数扩大，扩大再做 B / D。

### D14. 研究方向：隐藏信息进入搜索（待逐项验证；立项前查文献）

1. **双向信息建模（首选）**
   - 问题：树中对手看穿我方全部配置，导致"藏牌"（暂不太晶、不暴露克制招式）在搜索里没有价值。
   - 做法：对手先验的翻转视角前向遮住它看不到的我方信息（只留已暴露的，或换成对手视角的信念采样；遮蔽机制 `--mask-hidden` 已有），之后再扩展到对手视角的价值。
   - 验证：对战对比，并统计太晶 / 关键招式的暴露时机是否推迟。
2. **身份条件化 + 人类模型陪练**
   - 输入 = 我方身份、对方身份：`人类@赛前分数`（已有）、`bot@第 g 代`、`未知`。
   - 用处：自对弈的陪练按比例取历代 bot 和"人类@各分数段"；classifier-free guidance 外推作为我方先验：π ∝ π(·|高分)^(1+w) / π(·|未知)^w；辅助头从历史预测对手身份 / 分数。
3. **学出来的信念 + 观察一致性过滤**
   - 已知：网络的对手配置头在未暴露字段上比信念单次采样准（道具 64.9% 对 48%，太晶 42.1% 对 32%），而且不依赖输入里的信念样本。搜索仍然需要信念模型提供完整、一致的世界。
   - 路线：① 用网络给信念模型的候选配置重新加权（后验 ∝ 信念先验 × 网络打分）；② 生成式配置模型（MaskGIT 式掩码补全，以对局历史为条件），最终替代信念采样器；③ 用出手顺序和伤害数值剔除矛盾世界（粒子滤波）。
4. **同时出招的博弈论搜索**：节点上用 regret matching 产生混合策略，用网络先验加速。

**推荐顺序**：1 → 2 → 3 → 4。

## 7. 风险

| 风险 | 缓解 |
|---|---|
| 自对弈收敛到"对付自己"、循环 / 遗忘 | 人类数据锚点；更早各代的抽样；每 3 代对 3 代前、每 9 代对 Foul Play；陪练里放历代网络和人类模型（D14-2） |
| 慢性退化（每代都略弱但测不出） | SPRT（H0 弱 20 Elo）；每 3 代的累计检查回滚 |
| 价值头过拟合 / 被人类数据带偏 | 每代在新对局上检查价值（D15-7）；价值目标的子采样 / λ 回报 |
| 推理拖慢搜索 | 结构改动以搜索的叶子速度为约束；Rust 与 PyTorch 一致性检查 |
| 评测噪声 | 配对赛程 + 置信区间 + SPRT；离线指标看种子方差 |
| poke-engine 不保真 | 只作搜索用的近似模型；对局在 Showdown 上跑；fallback 记账（`search_fallbacks`） |
| 环境变化（禁用名单、新宝可梦） | 组队按时间加权、校验器按今天的规则；补新数据 |
| 许可 / 规则 | Metamon 数据非商用；Foul Play 为 GPL；Showdown 对 bot 的态度模糊 |
